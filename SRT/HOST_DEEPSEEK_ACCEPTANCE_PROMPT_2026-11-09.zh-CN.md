## 执行方式

- 使用当前 Host 的系统说明、App 页面和实际附带的 Tools／Schema，按顺序调用；每次操作后读取结果和下一轮最新 View，不在一轮内预先发出依赖新页面的调用。下面的工具名是能力提示，实际完整名称和参数以当前 Tools 为准。文件操作使用 IDE，不用其他文件工具替代。
- 只操作本轮创建的测试计划和一个全新的验收目录，不修改现有业务数据或项目源码。使用唯一标记 `AOTUI-验收-<本轮时间>`。从当前 Workspace 确认验收目录；不明确时，只请我提供新建空目录的绝对路径，已明确就不用再问。

- 每项按「通过／失败／受阻／未执行」记录。没有发出的调用不算验证成功；能看到的事实和推测分开。实际异常保留一次完整记录，其他独立项目继续；不要用反复重试覆盖第一次失败。

## 1. 当前入口与基线

根据实际入口打开 Planning 与 AOTUI IDE，记录当前可见的 App、View id／type 和相关工具名称。App 控制可查找当前的 system-open_app／system-close_app，app_id 取实际枚举。缺少 App 或入口就指出，让我检查本聊天的 Apps 是否启用，继续可执行部分。

区分 Root 的静态工具名称目录与当前可调用的 Tools。Host TUI 面板可能预览未启用 App，不能拿预览证明模型能调用。当前没有 PlanDetail／FileDetail 时，相应类型工具不应激活；如果存在此前打开的页面，保留它们，说明这一基线条件未构造，不为测试关闭我的其他工作。

## 2. Planning：Ref 操作与最新状态

创建两个测试计划 A、B，名字均带本轮唯一标记。A 含“设计”“交付”两个阶段，“设计”中放“整理需求”“核对清单”两个任务，“交付”中放“交付检查”任务；B 含一个阶段和一个任务，名称带 `B-保持不变`。保留至少一个未完成阶段，方便后面定位。

打开 A，使用当前页面给出的 Ref 修改“整理需求”的标题，完成该任务，再完成“设计”阶段。每次都重新读取当前页面，用标题识别下一步对象，不沿用数组旧索引。

检查并记录：

- 计划／阶段／任务的对象选择使用 Ref，无须抄写 plan_id／phase_id／task_id。
- 展示保留类型与局部引用，例如 `[设计](Phase:completed_phases[0])`；调用使用实际所在 View 的 `id` 加局部名，例如 `实际ViewId.completed_phases[0]`，输入不带 `Phase:`。普通标题、内容和文件路径仍按各自 Schema。
- 任务与阶段变化进入最新 View；同一个 App／View 不存在两份都代表当前状态的页面。聊天中的历史工具卡片、操作收据不算重复当前 View。
- Tool Result 提供结果／提示，主要业务状态从 View 读取。保留一次真实 Ref 输入、对应展示片段、工具结果与更新后的页面片段。
- 完整工具说明和参数 Schema 来自当前 Tools；Root 可以按类型列工具名，Planning 数据页不重复整份工具定义，也不出现 Mutating 分类。

## 3. Planning：对象切换、错误恢复与关闭

打开 B，按 B 当前页面的 Task Ref 修改它的任务标题；再打开 A，确认 A 的状态未被这次修改影响。Planning 同时只激活一个 Plan，这一步验证切换对象，不能据此宣称验证了“两份 PlanDetail 同时发布同名 Ref”。

在 PlanDetail 工具可用时，做一次明确的错误类型负例：把当前页面实际存在的 Plan Ref 放进 update_task 要求 Task Ref 的参数，拟将标题改为 `TYPE-ERROR-MUST-NOT-APPEAR`，其他参数合法。记录是否真实发出调用及错误码／提示，检查业务状态未改变；再使用当前正确的 Task Ref 完成一次正常修改。若调用入口阻止发送，如实记录为未执行后端负例，不绕过限制，也不编造 Runtime 返回。

调用 close_plan。它关闭唯一激活的计划，空参数是当前正常合同，不算缺少 Ref。检查 PlanDetail 退出当前投影、最后一个 PlanDetail 关闭后其类型工具撤销；PlanList 及 close_plan 仍可存在。然后从当前 PlanList 重新打开 A。

不要用“关闭重开后，相同 Ref 字符串仍能调用”判断旧观察失效失败：新观察可能重新发布同名 Ref。Host 未暴露旧 Observation／调用凭据时，旧资格撤销记为本轮不能直接验证。

## 4. IDE：两个文件、最新 View 与语言工具

将本轮空目录加入 IDE 工作区。通过 IDE 创建 `a.ts`、`b.ts`：a.ts 含简单函数及 `A-v1` 标记，b.ts 含 `B-UNCHANGED`；在一个字符串中保留中文、`<A>` 和 `&`，用于检查正文显示。

create_file 会直接打开文件页。创建后先关闭本轮两个 FileDetail，观察无文件时编辑工具撤销；再先打开 a.ts、后打开 b.ts，记录两个 View id，确认工具随页面出现且按类型共享。若另有非验收文件打开，如实说明无法构造无文件态。

按实际 Schema 将 a.ts 的标记改成 `A-v2`，确认 a.ts 的最新 View 更新、b.ts 内容不变。正文应正确保留中文、`<A>`、`&`，不能出现重复框架外壳或错误的转义显示。

关闭 a.ts，保留 b.ts，确认共享编辑工具仍在。使用仍在的 write_file 尝试一次写已关闭的 a.ts，内容为 `CLOSED-FILE-MUST-NOT-CHANGE`：预期拒绝，当前错误码应为 IDE_FILE_NOT_LOADED。不要先替它重开。随后重新打开 a.ts，确认仍有 `A-v2`；若意外写入成功，记失败并停止对该文件继续写入，保留现场。文件参数使用绝对路径，不强行包装成 Ref。

可选补充：调用一次当前提供的 lsp_hover，位置使用完整文档的一基行列，在 FileDetail 语言面板核对真实符号／类型说明；若选择定义跳转，则核对目标文件／位置。记录实际结果或不可用原因，只验证本次本地使用。

## 5. 我配合：外部修改与界面检查

按预期拒绝后，用 multi_open_file 重新加载 b.ts，确认 `// EXTERNAL-CHANGE` 仍在，再基于当前内容将标记改为 `B-external-plus-agent`，保留外部注释。refresh_workspace 只刷新目录树，不能代替重读正文。记录错误是否可理解、恢复是否成功；不要求 Runtime 自动轮询磁盘。若旧写入意外成功或结果表示 unknown／partial，先记录并停止该文件的后续写入，核对实际状态，不能用后续成功覆盖第一次异常。

## 6. 我配合：停止与继续

先告诉我：“下一条请发‘开始暂停测试’，在我工作时点击 Host 的 Pause Agent。”收到后，重新打开并读取 b.ts，再在下一轮说明它的内容，不写文件。我会在工作期间点击暂停。已经开始的模型请求及该轮工具允许完成；验收重点是暂停后不再自动进入后续轮次，不能把在途输出判为失败。

我会在暂停时发送：“继续验收：请回复 MC-RESUME-OK 和当前 b.ts 正文，不修改文件。”待在途工作结束，观察新请求没有自动开始，再点击 Resume Agent。恢复后应处理该请求并按当前 View 报告内容。是否命中暂停、恢复是否正常由我补充观察；按钮不可点或未赶上就记未执行，不反复调用或制造长任务。暂停不要求回滚已完成操作，也不能从模型感觉推断底层请求次数。

## 7. 关闭与最终报告

关闭本轮仍打开的 FileDetail；若没有其他 FileDetail，相关类型工具应撤销。再使用当前 system-close_app 关闭本轮专用 IDE，记录真实收据，确认其运行页面和业务工具退出当前上下文，不能仅据此宣称底层资源全部归零。若 IDE 还承载其他工作，保留它，将 App 关闭记为未执行。关闭本轮激活的计划，再用当前 PlanList Ref 打开 B、确认正常后关闭，验证 IDE 关闭后 Planning 仍能工作。
