## 1. 你负责的目标与范围

AOTUI App 的服务对象是 LLM Agent，SDK 的核心开发者也是 Agent。我们希望它成为可被不同 Agent 系统广泛采用的基础设施，类似 Linux / shell、Chromium / HTML + JS + CSS 在各自领域提供的稳定基础。

这个目标落实为三项要求：

1. 使用 App 的 Agent 能正确理解当前页面、选择对象、调用适用操作，并理解失败及恢复信息。
2. 开发 App 的 Agent 能靠公开 SDK、类型、文档和诊断生成、修改、修复正确应用，不依赖内部知识和重复接线。
3. Runtime 提供稳定的共用交互语义与可靠运行行为；业务责任留给 App，内核保持简单、强大、稳定。

当前重点是 SDK 和 Runtime 的概念、系统、模块、机制及实现。为核实真实请求和兼容性，可以追踪直接消费者，例如 agent-driver-adapter、agent-driver-v2 与示例 App；不要顺势重构整个 Agent Driver、业务应用或 Host 产品。

## 3. 必须保持的产品与运行约束

### 页面、上下文与操作

- AOTUI 用 XML + Markdown 组织 View，并包装为 Messages 中的 User Message。这些内容既表达外部事实，也是 Agent 对事实的记忆；Agent 只能通过应用允许的有限操作改变这部分内容。
- 一个 View 实例就是 GUI 网站或桌面应用中的一个页面。它可以展示多个对象、切换当前业务对象，不强制“一页永久对应一个对象”。
- 当前投影中同一逻辑 View 只保留最新有效快照。成功观察完整包含该来源的全部已打开页面；历史收据、用户对话和在途调用的旧来源持有分别处理。
- Tool 按 App + ViewType 共享定义；同类多个实例各有 context、绑定与启用条件。工具动态暴露不能替代调用资格、Host 授权及 App 业务权限检查。
- Tool 发起操作并返回结果、提示和恢复信息；主要业务数据与变化经 View 呈现，保持类似 CQRS 的职责分离。
- 一次生成的模型输入已冻结。后台准备、发布、观察采用、实际发送是不同事实；外部变化不会自动进入正在进行的生成。

### Ref、资格与业务状态

- Ref 显示与调用格式必须保持不同。页面 `files` 显示 `[测试文件](File:results[0])`，工具参数调用地址为 `files.results[0]`；接收页面可以是 `view_id: editor`。来源页与接收页独立。
- 保留同一 App 运行实例、同一原 Observation 内跨 View 传 Ref，以及单值、整数组、元素、有序且可重复的多选、optional。普通路径和正文不强制 Ref 化。
- Ref 从调用绑定的原 Observation 取值；handler、context 与服务使用当前有效执行绑定。不冻结任意业务闭包，不把旧 Ref 偷换成最新数据。
- App 负责业务对象存在性、版本、归属、权限、冲突和恢复。Runtime 不能替文件系统或外部服务保证业务写入原子性，也不能猜模型真正想选哪个合法对象。
- 采用新观察会撤销同一 App 实例旧观察的新调用资格；后台发布或预览不会自行采用。多个 App 分别采用，不自动形成全局事务。资格撤销与在途来源释放分开，在途责任到真实终点才收尾。
- 超时不代表未执行或取消成功；handler 返回、业务效果已知、投影成功和物理资源退出也不相同。不盲目重放，不承诺进程重启后的 exactly-once。

### 当前明确边界

- 默认作者方式保持 Preact；Node Worker 继续是默认托管路径，运行可信 App，不是文件或网络权限沙箱。
- 先做好单 Agent 独占 App 实例、串行 Tool Call 主路径；不借机建立多 Agent 共享调度器。
- TypeBox 和现有有限 Schema profile 继续作为作者基础，不新造 DSL，不默认追求完整 JSON Schema。
- 持久化是显式启用的小型 JSON 状态服务，业务数据及迁移归 App，不扩张为通用业务数据库或 Agent 检查点系统。
- 不恢复 `Mutating`、`isMutating`、`effects`、`failureEffects`、`recoveryTool` 或同义框架分类。
- **开页准入、rollback 和恢复状态机的重设计明确暂缓。** 保留和解释现有分支，不从其他优化顺带决定它。
- CLI 替换 Tools、descriptor、独立 contracts 包、第二种执行后端、AST、增量传输及共享内存仍是候选；没有整体实施决定。

## 4. 最近 Review 留下的有效起点

这些是上一轮核查结果，使用前结合当前代码确认。完整证据及限制在 Review 回复和对应议题中。

- **03 装配：** 纯 Core 已存在，默认 SDK 作者也已获得封装。问题集中在非默认集成者承担的身份、frame 接纳、执行绑定和关闭接线。AppKernel 是现有起点；`AppExecutionSession` 只是候选名称，不能再造一层重复 owner。
- **01 请求：** 默认 adapter 已有部分 adoption 失败处理，Driver 已有采用失败不调用 provider 的测试，配置预算时会检查实际输入。待补的是更完整的多 App 正文、Tools、alias、预算和失败收尾组合证据。
- **04 收据：** 默认 adapter 已透传 App 原始错误码、message 和 data。不要只看顶层 `TOOL_FAILED` 就判断信息全丢失；继续核实恢复字段与执行阶段的实际消费者。
- **06 Preact：** 已有共享队列下的多 App 根失败隔离检查。未来同进程后端还需解释 globals、document 事件、独立关闭和待提交工作的所有权；相同错误码也不等于相同健康后果。
- **07 XML：** 已确认 NUL 可通过当前 Core 字符串校验，但输出不满足标准 XML 可解析性。输出边界的拒绝或显式可见编码仍待选择，不能静默改事实，也不能因此全局缩小 Core JSON 值域。
- **09 Schema：** 模型表示会丢失已有 Ref 类型和值形态提示。优先使用显式 refType、受支持值 Schema 和作者说明，不猜 TypeBox 变量名。迁移 `modelToolSchema` 时核对 SDK 声明、Runtime defineTools、静态目录、最终模型表示四处消费者，并保留早诊断和各层容量责任。
- **11 Ref 范围：** 捕获、grant、主正文和最终 Messages 的范围不同。当前 adapter 追加已授予 Ref 目录；捕获 100 项却只画 10 项不代表只提供了 10 项。根数组也可能被选择。
- **05 公开承诺：** Observation 的 `entity` 类型分支与当前 snapshot-value 生产路径不一致，是收窄候选；仓内没有正常消费者不证明外部无人依赖。类型、包、源码、已构建产物及模型别名的兼容承诺须区分。
- **12 性能：** 优先评估省掉 prepare 与 unchanged 分支中未消费的摘要计算，保留已发布 `contentDigest` 的字段及结果。其他优化各自依赖证据，可以在最小改动后停止。
