# AOTUI 的 SDK 与 Runtime 值得把什么做成基础设施

2026-11-18 逐篇架构评审。依据设计索引及十二篇原文（修订 0.2），对照提交 `90449dc2d7` 的 SDK 0.9.0、Runtime 8.0.0。下面记录我的判断与建议，各议题的决定状态以原文为准。[设计索引](README.md) · [SDK 作者合同](../../sdk/README.md) · [Runtime 宿主合同](../../runtime/README.md)

**我会保留目前的核心交互模型。模型这一轮看见了什么、刚才选中了什么、执行时还允许做什么，都应当有可靠答案。** 文件列表、编辑器、审批台都需要这些答案。如果每个宿主都要自行拼接，AOTUI 很难成为共用设施。SDK 让 Agent 作者容易写对页面，Runtime 让不同宿主重现同一行为，Preact、Worker 和存储实现才有独立演进的空间。

## 01 · Messages 同时是外部事实和 Agent 的记忆

**我的理解。** Agent 调用 IDE 的打开文件工具，收据告诉它 `test.txt` 是否打开成功。正文通过一条 XML 包装的 Markdown User Message 进入下一轮模型输入。Agent 随后还能回到这份文件继续工作。关闭页面，也就改变了未来输入里保留的工作材料。这里“修改记忆”有明确的操作范围。Agent 向应用表达打开、关闭、选择或编辑的意图，应用更新状态，框架只替换属于这个应用的投影。即使同为 User Message，页面正文和用户亲自给出的任务也有各自的来源。

**设计的优点。** 它解决了多轮工具调用里的一个具体难题。一个文件改了三次，如果三个返回值都包含全文，模型还要从历史里猜哪份有效。当前投影中每个已打开页面只保留一份最新有效快照。成功收据在保留期内仍能说明前两次编辑发生过，有长期审计需求的宿主可以另存历史。Runtime 也能为已分发的调用保留旧数据，直到调用结束。这三种保留规则对应当前工作、过去的操作、尚未结束的责任，彼此可以同时成立。

**最容易讲错的是“最新”。** 同一次编辑要经过几个时刻，每一步能证明的事实都有限。

| 时刻 | 哪一方知道什么 | 对 Agent 的实际含义 |
| --- | --- | --- |
| 模型请求携带观察 O1 | 输入显示 `test.txt` 版本 7 | 这次生成只依据已经送入的材料 |
| 磁盘变成版本 8，IDE 得到通知 | App 可以更新业务状态并提交新页面 | 当前这次生成仍看不见版本 8 |
| O1 的调用抵达 | Runtime 知道所选值来自 O1，IDE 能检查当前文件 | IDE 可以据业务规则拒绝覆盖、合并或执行 |
| 写入完成，但页面生成失败 | 收据可以确认写入，投影同时处于故障状态 | 应从业务实况修复页面。再执行一次写入可能重复产生副作用 |

**文章留下的缺口。** 文中把“采用并用于请求”并在一句话里，日常阅读很顺，写宿主时却是两个动作。采用会撤销旧观察的新调用资格，之后网络发送依然可能失败。两个 App 也各自采用。本次用两个纯 Core 实例主动释放 B 的新候选，再依次采用 A、B。A 切换成功，B 拒绝，旧 A 已失效，旧 B 仍有效。这个构造说明单实例语义怎样组合，不能据此断言某个现用 Host 已经发错请求。[观察注册与采用](../../runtime/src/core/invocation/observation-registry.ts)

**我的改进建议。** 保留统一投影主路径，在 Runtime 的模型集成例子中走到“实际请求”这一步。使用同一候选生成页面 Messages、带 `view_id` 的 Tools 和本轮别名映射，加入对话、其他来源及预留输出检查总预算，再采用并发送。部分采用失败就放弃这份尚未发送的请求，释放不用的候选，按实际有效来源重新准备并复查预算。集成者先有一个正确样例即可，重复接错才值得收为公共 helper。跨 App 事务、模型已读回执和完整事件日志都引入了新的状态所有者，本文的案例用现有机制就能解释。

**怎样验证。** 一个记录实际请求参数的模型替身就足以检查 O1、O2 分别携带哪份正文、哪组工具，以及预算失败是否真的阻止发送。另看真实 Worker 的失败用例，业务调用次数保持为 1，单纯重绘无关页仍失败，App 修复后才成功观察。前者是建议补的集成证据，后者本次已运行。[议题 01](01-messages-facts-and-memory.md) · [真实 Worker 的投影恢复用例](../../runtime/src/engine/app/worker-host.projection-refresh.e2e.test.ts)

## 02 · View 是页面，同一页可以切换业务对象

**我的理解。** 一个审批页可以列十张报销单，一个搜索页可以换关键词，一个编辑页也可以从 `test.txt` 切到 `notes.txt`。页面身份回答“哪个页面接收调用”。页面内容回答“应用这一次展示了什么”。业务参数回答“用户打算操作哪个对象”。将三者区分开，是撤回“一页永久对应一个业务对象”最充分的理由。页面语义已经确认，应用组织页面的方式依然有选择。

**设计的优点。** 按 App + ViewType 共享工具定义，多开一个编辑器会增加该页的正文、Ref 和执行绑定，模型只需接收一份共享业务 Schema。可接收页面的范围仍可能随之变化。每个实例拥有自己的 `context` 和启用条件，模型用框架注入的 `view_id` 选择接收页。最后一个可用实例关闭时，工具自然退出。这很好地表达了 GUI 里的常识，也把稳定的工具说明与经常变化的页面状态分开了。

**真正的风险是选错对象，且所有框架检查都可能正确通过。** 设编辑工具只有 `replacement` 参数，handler 从 `context.currentFile` 取目标。模型想改刚才读到的 A，调用抵达时同一页正在显示 B。若工具定义的意思确实是“修改执行时的当前文件”，它可能合法地改到 B。`view_id` 只能选中仍有效的页面。若写入必须以所见版本为准，IDE 还应在实际写入边界使用它能提供的版本检查。SDK 无法替文件系统或远端服务保证这段时间无人改动。

| Agent 的意图 | 推荐的 App 表达 | 代价与适用处 |
| --- | --- | --- |
| 切换当前页面的换行显示 | 只传 `view_id`，在实时页面状态上操作 | 参数最少，切换文件后这个动作仍然合理 |
| 修改我刚才选中的文件 | 显式接受文件 Ref，用原观察值识别目标，必要时检查所见版本 | 多一个有意义的选择，能保护跨页、跨时刻的写入意图 |
| 同时比较和编辑两个文件 | 每个文件开独立页面，各自保持编辑状态 | 操作直观，但两页正文都会占据模型上下文，外部冲突仍由 IDE 处理 |

**源码和实测。** 在纯 Core 中，我分别构造了没有详情页、两个同类型详情页、关完全部详情页的状态，观察到共享操作数为 **0 → 1 → 0**。保持原观察有效，将 `editor` 和来源列表首项都从 `test.txt` 更新成 `notes.txt`。一笔源于旧观察的调用，handler 读到当前页面 `notes.txt`，显式 Ref 却仍然是 `test.txt`。再关闭 `editor`、以同名重建，旧调用得到 `VIEW_INSTANCE_REVOKED`，handler 没有再进入。这是页面连续性、业务目标及关闭重建三种事实的直接证据。[实例绑定](../../runtime/src/core/tool/view-owned-tools.ts) · [原观察参数解析](../../runtime/src/core/tool/snapshot-value-arguments.ts)

**我会怎样改。** 给 Agent 作者并排放两个可运行操作，一个改“当前页面显示”，一个改“观察中选中的对象”。在外部文件版本已变时，让第二个操作展示一个可行动的业务冲突。动态能力仍按实例启用，实际执行要检查原观察是否授予、当前挂载和激活是否有效、Host 是否授权，最后由 App 核实业务前置条件。只有几个独立应用都需要同一种导航后撤销行为，再考虑薄 helper。现有页面、Ref 与 `context` 已经能表达上表三种设计。[议题 02](02-view-page-semantics.md)

## 03 · Core 的纯净度与公共装配粒度

**我的判断。** 这是十二篇里最适合先讨论的系统问题。今天已经可以在没有 DOM、Preact 或 Node Worker 的情况下运行 Core。迁入另一个 Agent 系统的昂贵之处在于，集成者要学会哪些调用必须成对、按序、在同一个实例上发生。纯 TypeScript 使代码可搬运，将这些成对责任收拢才能使它容易被正确采用。[Core 入口](../../runtime/src/core/index.ts)

**用一次提交来区分必要复杂度与可以消除的复杂度。** 公开 Core 样例先调用 `prepareFrame` 获得页面实例和工具绑定，再把它们写进页面和 Ref，交出 `candidate.accept`，最后发布快照。每一步都有道理。若某个集成者先换掉了实时 handler，页面和 Ref 却随后验证失败，模型可能还看着旧页，执行端已经切到另一套绑定。现有官方路径把接纳控制在验证通过之后。让每个集成者自己维持这个顺序，是可以省掉的公共负担。[独立消费者样例](../../runtime/tests/fixtures/public-core.ts) · [提交协调器](../../runtime/src/core/projection/coordinator.ts)

**原文提议的优点。** 它没有把默认 SDK 作者和高级集成者混在一起。用 `createTUIApp` 的作者已经不用手写注册表。也已有合适的内部起点，`AppKernel.prepareFrame` 知道如何将当前实例的页面、Ref 与工具编成一次提交，`onClose` 知道本实例该如何清理。先让已有实现承担这份责任，可以使 Worker 路径和将来的第二条路径遵守同一规则。[现有 AppKernel](../../runtime/src/worker-runtime/app-kernel/AppKernel.ts)

**我担心的过度设计。** 原文的 `AppExecutionSession` 很容易演变成对现有对象的第二层包装。若它新增一个 `closed`，同时 interaction、App 生命周期和 Worker 都保留各自的关闭状态，开发者反而多了一个需要解释的“已经关闭”。我会要求提案逐项指出，新单元接手了谁的状态，谁因此停止写入该状态。若只能列出转发的方法，保留现状更容易维护。

| 长期责任 | 唯一有条件作判断的一方 | 装配入口应带来的简化 |
| --- | --- | --- |
| 当前 App 实例、实时页面绑定、本地提交 | 执行端，已有 AppKernel 可承接 | 提交完整页面时，由执行端一并接纳对应绑定，消费者无需亲自安排先后 |
| 已收到哪个快照、采用哪个观察、何时释放持有 | 调用端 interaction 与它使用的快照存储 | 消费者能以一个实例操作，并将调用追溯到原观察 |
| 通道是否交付、物理资源是否退出 | 实际执行后端 | 直接返回可等待、可核实的结束结果 |
| 文件、订单、业务数据如何恢复 | App | 可选持久化只在 App 启用时提供，业务语义留给作者 |

**建议与验收。** 当下沿用默认托管入口，把底层样例当成测量集成负担的工具。现实中如果出现第二处同样的执行装配，先抽到内部，待一个独立消费者使用后再决定公开哪些原语。验收时移走样例里的手写 `ExecutionBinding` 和 frame 接纳接线，检查同名页重开、提交失败、关闭时尚有调用这三个场景。三者仍然正确，且使用者不用知道内部先后顺序，才值得承担新入口的兼容责任。默认单 Agent、串行调用已足以检验这一设计。[议题 03](03-core-assembly.md)

## 04 · 将应用生命周期与 Node Worker 分开

**我的理解。** 使用者真正希望可替换的是“在哪里运行业务”。在本机 Worker 或一个受信任的同进程环境中，页面的身份、原观察 Ref、已启用工具的含义都应一致。两种环境在故障时能证明的事情却不同。Worker 可以报告线程实际退出，同进程的代码如果还在执行，给 `close()` 返回一个已完成的 Promise 并不能使它停止。这个差异值得保留在报告里。

**原文的优点。** VS Code Extension Host、LSP 等先例提供了一个恰当的参照。运行位置和应用协议可以分开，但机器之间传得通消息，仍解决不了 AOTUI 特有的问题。比如 `postMessage` 已返回、另一端已接纳该投影、Host 已用它请求模型，是三个不同的事实。若用一个笼统的 `flush` 表达，换一个后端，Host 就可能拿到不同含义的“刷新完成”。我赞成把刷新承诺落在调用端可以实际观察到该提交的位置。[Worker 发布路径](../../runtime/src/worker-runtime/index.ts) · [调用端 Worker 生命周期](../../runtime/src/engine/app/worker-host.ts)

**从一次有副作用的操作看失败。**

| 已掌握的证据 | 对 Agent 诚实的结论 | 有意义的后续动作 |
| --- | --- | --- |
| 分派前因页面已关闭而拒绝 | 此次 handler 没有进入 | 重新观察，选择仍有效的接收页 |
| 已分派，等候超时或通道在无终态时断开 | 业务可能已经执行，可能仍在进行 | 在保留期内用原 `observationId` 和 `invocationId` 查收据，按 App 提示核对外部结果 |
| handler 已返回业务成功，但页面发布失败 | 业务结果已知，呈现有故障 | 修复呈现，用下一次成功观察确认当前数据 |
| handler 确实返回，App 却报告“上游没有确认” | 框架知道函数返回了，具体外部效果仍由业务证据决定 | 保留 App 的错误码和恢复信息，交由业务方核对 |

**我对现有机制的批评。** 最后一行尤其容易丢失。handler 已进入并返回时，`success: false` 会映成 `failed / TOOL_FAILED`，原始错误在详情中。只把顶层状态显示给 Agent，会把“无法确认上游结果”读成“可以重做”。短期应先让集成样例把应用错误、恢复提示和执行阶段如实带到用户可见的收据里。这个问题目前用已有数据就能改善，无须恢复 `effects` 或让 Runtime 推断文件、支付等业务是否可重试。[收据映射](../../runtime/src/core/invocation/invocation-outcome.ts) · [应用返回值](../../runtime/src/core/tool/tool-result.ts)

**我对候选后端接口的取舍。** 先保留 Node Worker 默认路径。只有脚本加载或部署差异时，现有 Worker 注入点就值得用。等有实际部署需要同进程或其他执行位置，再共享 03 的应用执行装配，让后端仅负责加载、交付、断连和实际释放。文中“启动中途失败”的归属，我倾向由已分配资源的后端继续负责清理，直到确认释放，并向调用者报告可核对的结果。把半初始化句柄丢回普通集成者，会让每个宿主都重复学一次清理协议。

**验收与眼前可改之处。** 比较后端时，注入“操作已进入但回执没到”和“启动失败时线程仍存活”两个故障，再看报告是否与所掌握的证据相符。今天还能先修一处文字错位。Runtime README 明确默认 Worker 托管可信代码，内置模型指令却用 `Worker-Isolated` 和 `for safety` 描述它，容易让人高估文件和网络权限隔离。将文字收敛到真实的线程与生命周期保证，是一项比发布后端 SPI 更小、更确定的改进。[议题 04](04-execution-backend.md) · [内置模型指令](../../runtime/src/adapters/system-instruction.ts)

## 05 · 用什么兼容承诺让第三方敢于发布 App

**我的判断。** 成套发布适合现在快速迭代，长期生态需要一个更具体的承诺。假如 Runtime 只替换了快照存储结构，别人去年发布的 IDE 是否还得重编、重发、通知用户升级？如果答案总是“需要”，每次改内核都要全生态协作。对基础设施来说，这是比多维护一个内部模块更昂贵的成本。原文已确认收窄承诺的方向，首个合同标识、支持期和拆包方案仍待决定。

**原文做得好的地方。** 它把“兼容”拆成了可以独立验真的三种承诺。

| 对象 | 哪种证据有效 | 一个容易误判的结果 |
| --- | --- | --- |
| App 作者源码 | 用新 SDK 编译旧源码，并跑它依赖的交互行为 | 类型检查通过，但运行时 Ref 改指最新值 |
| 已分发的 App 产物 | 原封不动的 JS、清单和既定依赖组合，装入受支持的新 Runtime 后运行 | 测试时悄悄重编、改了清单或经源码别名换掉了旧包 |
| Host | 使用公开入口完成观察、预算、采用、调用、查收据、关闭 | 只见页面预览正常，实际发给模型的工具参数已经变化 |

**当前的硬约束。** `@aotui/sdk` 精确依赖 Runtime 8.0.0，默认作者路径还使用 Runtime 的参数编译与 DOM 适配。仅把版本范围放宽，安装器就可能选出未经行为验证的组合。反过来，即使类型全搬进一个新包，只要旧 App 加载时还会走旧的运行时依赖，这个新包依旧无法证明可独立升级。验收须记录 App 和 Host 两侧实际解析到的版本，以及 App 和 SDK 是否共享受支持的 Preact 模块实例。[SDK 包依赖](../../sdk/package.json) · [Runtime 包入口](../../runtime/package.json)

**我支持的 Breaking Change。** 发布前先按真实消费者收窄公开面。例如 `Observation.refs[].kind` 的类型允许 `entity`，同一实现的快照只会产生 `snapshot-value`。它会让编写 Host 的 Agent 为一个实际取不到的分支生成代码。查完受支持消费者后，一次迁移并删除这类多余承诺有正收益。另一面，执行前的实例检查、跨 Worker 的来源检查都有实际职责，即使名字或位置改变也应保留。清理的标准要看可观察行为及其使用者。[Observation 类型](../../runtime/src/core/invocation/observation-types.ts) · [Ref 目标类型](../../runtime/src/core/snapshot/types.ts)

**建议的顺序。**

1. 先选一个已构建的代表性 App 作为将来检验对象。写下它依赖的最小语义，包括页面可切换、同类工具共享、原观察引用、失效后如何告知调用者。
2. 真正开始对外承诺兼容时，同时定下首个基线和有限支持期。一个可判定的标识已够用，清单与工厂从同一处生成。两者冲突应给出可定位的错误，已有快照或 Worker 协议标识仍在自己的边界生效。
3. 每次只改 Runtime 内部时，在干净安装中跑那份原产物。等 SDK 的运行时依赖已经归位，并有一次真实独立发布需求，再决定是否增加合同包。需要表达第二个兼容能力基线时，再考虑更细的版本字段。

**验收。** 我会在同一份旧产物上验证成功和失败两条路。成功路走到开页、跨页传 Ref 和编辑。失败路保留旧观察，关掉接收页后再调用，检查原来的失效语义。如果只有成功路，内部重构即使破坏了调用资格，兼容性测试也可能全绿。这项验证可以扩展仓库已有的安装包检查。跨版本行为仍要等第二个 Runtime 产物到位后实际验证。[议题 05](05-compatibility-and-distribution.md) · [现有安装包验证入口](../../runtime/tests/verify-installed-contracts.mjs)

## 06 · Preact 在什么时刻完成了一份可用的投影

**我的理解。** 屏幕上“看起来已经画好”和 Agent 可以安全发起操作之间还有一步。若列表换了排序，三个选项的文字可能相同，但第一个 Ref 已经代表另一个对象。页面正文、捕获的值和本次实例的工具绑定必须来自同一次真实提交。这个问题在服务 Agent 的 UI 上尤其重要，错配可以直接变成一次对错误对象的写入。

**现有桥的价值。** Preact 的 Option Hooks 有正式扩展点，把它们一概归为私有 API 不准确。困难在于 SDK 还要处理具体版本的内部字段、共享调度队列和异常路径，才能知道整棵相关子树何时可读。普通 TypeScript 入口已经能直接提供完整投影。两条作者路径给了项目一个很好的对照，同一交互语义可以由不同渲染技术产生。[提交桥实现](../../sdk/src/app-factory/render-commit.ts) · [普通 TypeScript 作者入口](../../sdk/src/app-factory/createApp.ts)

**当前的作者摩擦有个真实例子。** 仓库测试先把值设为 1，投影准备成功。再设为 1，Preact 没有产生新提交，准备调用以 `SNAPSHOT_INVALID` 拒绝，但上一次健康投影仍然健康。接着让组件渲染抛错，调用方同样看到 `SNAPSHOT_INVALID`，这次投影却真的记录了故障。两个表面相同的返回结果，对作者意味着不同的恢复路径。这个测试本次运行通过，恰好说明行为边界比“相同值更新算不算成功”更细。[公开作者 API 用例](../../sdk/src/public-api-contract.test.tsx)

**我的取舍。**

- **现在**保留默认 Preact，集中维护真实提交时机、hook 衔接、异常隔离与卸载。优先让错误解释清楚这次准备为什么没有完成，以及旧投影目前是否健康。使用者可以据此决定是否需要修复。
- **对 `unchanged` 保持条件。** 一个 App 明确知道某个页内操作没有改变状态，可以返回业务收据。框架若要对一次准备返回“未变化”，则要能证明该实例已有健康提交、相关工作已排空、没有待结算异常。只比较 DOM 文本或等固定毫秒数，都不能证明这些条件。
- **统一的是提交之后的合同。** 如果两个作者入口已有重复校验，可以共享现有 frame 与校验函数。把 VNode、活闭包或全局调度器放进公共 ABI 会让纯 TS 也承担 Preact 升级成本。SSR 可以生成字符串，自定义 renderer 可以换掉 DOM，两者都还需另行证明对持续挂载、Refs 和生命周期的支持。

**原方案还应考虑一个跨议题代价。** 04 提到同进程执行，06 用到同一 Preact 实例的共享 options。两个 App 共处一个进程时，A 的一次失败或关闭，不能让 B 的提交被提前认作完成。默认每 App 一个 Worker 掩盖了一部分共享环境的难题。若真启动第二种后端，拿同一 Preact 的两个根一起验，观察一个根报错后另一根能否继续正常提交，价值高于为兼容多个 renderer 先定义抽象类。

**验收与停止条件。** 用受支持版本的一份实际安装包验证子树提交、只有 Ref 改变、渲染或 layout 抛错、挂载关闭和多根隔离。若 Preact 升级只须改变这一处桥，已达到近期的解耦目的。只有升级持续牵动 Core、或确有组件模型表达不了的应用，再评估更换实现。这里的选择也无需对第 10 篇暂缓的开页政策下结论。[议题 06](06-preact-semantic-bridge.md) · [安装包的 Preact 提交检查](../../sdk/tests/package-consumer/verify-preact-commit.mjs)

## 07 · DOM 如何变成 Agent 能读的正文

**我的判断。** 这篇找对了边界，但迁目录的优先级应该排在确定输出合同之后。应用用组件还是直接写 Markdown 属于作者选择，Core 消费的已经是页面元数据和 `markdown-v1` 正文。各宿主最终都要把它渲染成模型可读的 View Message。若两种作者写法看似画出同一页，生成的 Ref、代码内容或 XML 却不同，生态最终会依赖某个具体转换器的偶然行为。

**现有设计的优点。** 组件页面和普通 TypeScript 页面可以共用同一个 XML 包装函数，来源信息取自显式元数据。正文里即使出现字面的 `<view>`，也应该呈现为正在编辑的文件内容。保留这个唯一的外壳边界，同时让 Preact 继续使用现有 DOM visitor，已经能覆盖许多场景。纯 TS 写一个普通文本页用不到 AST。[DOM 页面读取](../../runtime/src/adapters/dom-app.ts) · [View Message 包装](../../runtime/src/adapters/view-message.ts)

**一个文档尚未解决、可以复现的问题。** 我让纯 Core 接纳了依次由 `A`、空字符 `U+0000` 和 `B` 组成的三字符正文，发布与观察均成功。把该观察交给现有包装函数后，用 Python 标准库 XML 解析器读取，解析失败。对照正文 `x < 3 && y > 0` 走同一路径则成功。后者是实体转义问题，前者涉及 XML 允许的字符集合。就算把 Markdown visitor 换成成熟库，前一条链路仍然存在。这个实验说明互操作边界确实有缺口，无法从中推断某个 LLM 必然读不懂消息。

**改进应落在恰当的层。**

| 谁处理 | 应负责的例子 | 选错层的后果 |
| --- | --- | --- |
| App | 打开混有二进制数据的文件，选择十六进制或可读转义供模型查看 | 框架擅自替换原文件字符，作者以后可能把展示文本误当成源文件 |
| 作者适配 | 保留代码空白，选能包住正文反引号的代码围栏，让 Ref formatter 生成局部标记 | 换 serializer 后 Ref 变成普通字面文本，模型失去选择线索 |
| XML 呈现边界 | 对属性和正文编码一次，识别目标 XML 无法表达的字符 | 每个 App 各自预转义一次，会出现双重转义和跨宿主差异 |

我的建议是明确 XML 可表示的文本范围。对不可表示的正文或属性，在形成正常模型消息之前给出带 App、View 与位置的呈现诊断，原始业务数据由 App 保管。这个改动会影响过去能进入消息的字符串，适合明确记录为可观察行为变化。健康 App 的呈现资格按各自来源判断，故障 App 的完整页面也不能悄悄缺一页后当作成功。

**迁移取舍。** 我会用代码围栏、相邻行内节点、换行、特殊字符、Ref 标记和未知标签做一小组输入输出对照，写清哪些是承诺、哪些只是现有排版。确认现有公开入口 `/adapters/dom` 的消费者及迁移路径后，再把 visitor 和样例移至 Preact 适配边界。一次迁移先保持输出可比，格式修正另行列出。如果复杂表格或嵌套文档已迫使多人反复修 visitor，再以同一批样例比较 AST 工具的维护成本。兼容标准以这些可读、可调用的具体结果为准。[议题 07](07-dom-adapter-boundary.md) · [现有 HTML 转换规则](../../runtime/src/engine/view/transformer/visitors/html.visitor.ts) · [XML 往返用例](../../runtime/src/adapters/view-message.test.ts)

## 08 · Ref 属于哪一页，作者能否从代码上一眼看出来

**原文指出的是一种很真实的开发错误。** 在 Preact 中，作者很容易在 `FilesPage` 函数顶部调用 `useArrayRef`，然后返回 `<View id="files">`。按人的直觉，“我正在写 files 页”，这个 Ref 理应属于它。但 hook 执行时，这个 View 自己提供的 Provider 还在将要返回的子树里。没有外层 Provider 的情况下，现有 SDK 会报错。现行可靠写法是让外层组件创建 View，内层内容组件调用 hook。这种错误对以 Agent 为核心开发者的 SDK 很重要，因为错误写法既自然，也很像一般的组件代码。[当前 Provider](../../sdk/src/components/View.tsx) · [作用域诊断](../../sdk/src/contexts/view-runtime-context.ts)

**现有做法也有优点。** 列表被拆成搜索栏和结果面板时，子组件天然可以在本页登记自己的引用。现有 hooks 会跟随组件的更新与卸载，普通 TS 已有 `ref`、`arrayRef`、`formatRef` 和捕获函数。两条作者路径已经共用捕获与格式化逻辑。简单页面仍然缺一个容易写对的方式，让声明、显示和所属页面放在一起。

**候选方案的收益和隐性成本。** 文中的 `View.refs` 可以让作者在同一函数构造一个 descriptor，将它同时用于正文标记和页面声明。它能消除强制拆组件，也减少了局部名拼错的机会。代价是从此既可能由父页面 prop 发布，也可能由子组件 hook 发布。两处都叫 `results` 时若采取“后写覆盖前写”，渲染或卸载顺序就会决定调用得到哪份业务数据。我主张在同一页面复用现有重名检查并明确拒绝。跨页同名仍然合法。

| 情形 | 应在哪个时刻决定 | 需要保住的行为 |
| --- | --- | --- |
| 本轮 render 已构造 descriptor，随后 layout 改动原始对象 | 候选构造时捕获 JSON 值，实际提交成功后发布 | 正文和 Ref 对应这一次渲染，旧观察不随对象突变 |
| 列表重排、缩短，或子组件卸载 | 对同一页结算这次完整提交 | 新观察只包含这次发布的项目，旧调用仍按原观察和有效资格处理 |
| hook 和 descriptor 同名 | 由同一个页面登记机制核对 | 一次错误不能默默顶替已经登记的数据 |

**我建议先做哪一步。** 先把现有错误从“只能在 mounted View 内使用”改为直接指向修复动作，例如“将 hook 放进 `<View>` 的子组件，再由页面渲染该子组件”。附上仓库已有的正确样例。随后用相同任务比较“改进诊断和示例后的现有 hooks”与“薄的 `View.refs` 原型”。若前者已让 Agent 稳定写对，引入第二种公开写法就没有多少收益。若后者明显降低首次写错率和修复轮次，才值得承诺一个 prop。[现有 Preact 样例](../../sdk/tests/fixtures/work-items-preact.tsx) · [共用的 Ref 构造与捕获](../../sdk/src/app-factory/refs.ts)

**怎样证明没有拿能力换简洁。** 让 Agent 仅依赖安装包的公开入口写一个两页 App，分别试整数组、单元素、有序且可重复的多选、可选参数缺省和显式空数组，并跨页调用。再让一次 render 失败，确认上次有效观察和登记所有权没有被新声明污染。记录首次通过、修复轮次和私有 import。这是我建议的作者实验，尚无实测结果。render 回调和显式 binding handle 只在已有组合方式确实表达不了具体应用时再讨论。[议题 08](08-ref-authoring-scope.md) · [现有类型化 Ref 用例](../../sdk/src/typed-data-ref.test.tsx)

## 09 · 工具的一份声明，怎样同时服务 App 和模型

**我的理解。** 同一个 `target` 参数在两个位置长得不同，是这个设计的合理之处。模型提交 `files.results[0]`，handler 得到经过验证的只读文件值。框架插入并消费 `view_id`，业务作者只声明真正的业务参数。`defineViewType`、TypeBox 和现有编译器已经能从一份声明贯穿类型推导、注册与执行校验。这种单一来源应保留，语义与模型表示分层的方向已获认可。

**我实际发现的短板在模型那一侧。** 用同名参数 `target` 分别声明“一个 File”“一个 Task”“整个 File 数组”，保留其余条件相同。当前源码生成的三个模型 Schema 完全相同。三者都告诉模型填一个字符串地址、必要时带下标，默认描述却没有带出所需业务类型或期望的值形态。Runtime 在解析时仍会严格拒绝不合要求的值。代价在更早的环节就产生了，模型可能要通过一次本可避免的失败才知道应选哪项。[SDK 的 Ref 参数声明](../../sdk/src/tools/view-type-tool.ts) · [模型 Schema 生成](../../runtime/src/core/tool/tool-parameters.ts)

| 参数声明的意图 | 模型应提交 | 从原声明可以生成的简短提示 |
| --- | --- | --- |
| 选择一个文件值 | 一个地址，如 `files.results[0]` | 选择表示单个 File 的标记 |
| 选择整个文件数组 | 一个地址，如 `files.results` | 选择表示 File 数组的标记 |
| 逐项选择若干文件 | 一组地址，如 `["files.results[1]", "files.results[0]"]` | 数组中每项都是一个 File 的地址，顺序有意义 |

**我的改法。** 优先从既有 Ref 类型和目标值 Schema 派生这类提示，保留作者补充的业务说明。目标 Schema 允许多种形态时，提示也如实表达，避免硬猜。普通路径和标题仍按字面值处理。TypeBox 已提供作者语法，近期可以先把支持的子集和声明错误写清楚，例如不支持 `pattern` 关键词、允许参数名叫 `pattern`、`default` 只作注释。正反例能直接复用现有编译器核对。更长的提示会占据 Tools 预算，是否值得以真实错误率与新增 token 一起判断。

**模块边界还有一个实际依赖。** SDK 的声明捕获和 Runtime 的 `defineTools` 都会调用 `modelToolSchema` 检查生成后的容量。直接把函数搬出 Core，可能连同声明阶段的超限诊断一起丢掉。应区分通用业务声明的大小约束与特定模型表示的限制，把后者放在对应适配器验证。迁移时分别检查作者仍拿得到早期、可行动的诊断，Host 仍能拦住当轮加入可接收页面后过大的 Schema。原先的两处调用各有理由，必须先迁走责任。[执行端声明登记](../../runtime/src/core/tool/view-owned-tools.ts)

**关于工具名，我比原文更谨慎。** 当前用整份 App 声明判断同名操作，开关某个页面不会让别的操作突然改名。若下一版 App 增加 SearchResults 页面类型，并在其中声明同名的 `open` 操作，旧工具的短别名仍可能变成限定名。始终包含 App、ViewType 和操作名有利于跨版本预测，但现有模型适配器限制总长 64，全面改名还会影响旧提示和既有集成。我的选择是先保证同一份声明下的稳定性，将别名到语义 ID 的映射绑定原观察。只有 05 确定要承诺跨 App 版本的别名稳定，或真实使用暴露迁移成本，才值得全量切换。Root 中静态列出的名称不能充当当轮授权。[当前别名规则](../../runtime/src/adapters/public-tool-name.ts)

**动态 Tools 与 CLI 怎么选。** 原生 Tools 直接向模型暴露当下可调用的操作，Schema 可对输入给出结构性提示。一个统一命令入口可能缩短固定工具表，但动作发现、参数帮助和解析错误要在别处付费。若比较两种入口，我会从相同初始状态分别运行同一 App，以等价的观察、业务动作和授权条件作对照，让模型各完成“开文件、跨页选中、关闭后恢复”，记录成功率、错页或错 Ref 次数、恢复轮次及实际输入成本。原生 Tools 继续作为默认入口。若对照显示 CLI 有实际优势，再讨论引入方式，两者可以共用同一执行内核。[议题 09](09-schema-and-tool-naming.md)

## 10 · 开页设计暂缓，哪些事实仍须讲清

**我的判断。** 暂缓是这篇最重要的已确认决定。它避免在“旧页怎样处理、业务副作用是否已发生”没有产品答案时，先把某种恢复方式写进 SDK 的长期合同。暂缓的代价也真实存在，App 作者仍需面对当前不同失败分支。对作者负责的做法，是把可观察事实和保证范围写准确。

**这个例子为何值得保留。** 原文记录了一次历史复现。健康 Root 尝试增加一页 513 KiB 正文，准备返回 `failed / SNAPSHOT_SERIALIZATION_ERROR`。失败发布后 Store 进入 `degraded`，再用原观察调用 Root 的普通工具得到 `SNAPSHOT_UNREADY`，handler 没有进入。我核对了当前协调器与测试，代码中确实区分前段快照校验失败，以及后段满足特定条件的 `OBSERVATION_CAPACITY` 开页拒绝。前述完整 513 KiB 场景本次没有重跑。[协调器](../../runtime/src/core/projection/coordinator.ts) · [开页分支的现有断言](../../runtime/src/core/projection/coordinator.test.ts)

**现有说明的优点和缺口。** 普通 TypeScript 路径可以交一份可放弃的页面集合，成功后由 App 确认导航。Preact 路径先执行同步更新，在特定拒绝分支通过作者提供的 revert 恢复导航。SDK README 对“开页容量拒绝时恢复导航”的说明，对命中特定拒绝分支的情况有意义。站在 Agent 作者角度，“文件太大”看起来全是容量问题，读者很容易把这句话套到前面的 513 KiB 情形。这是措辞适用条件不够直观，单靠一个新的错误名也无法替作者厘清发生了什么。[SDK 的开页说明](../../sdk/README.md)

| 今天已经可以依赖的边界 | 对失败和恢复还需要区分什么 |
| --- | --- |
| 一次成功观察要包含该来源全部已开页面 | 一次新开页未成功后，原页面在各失败分支分别处于什么状态 |
| App 可以按固定投影限额分页、选正文范围 | 怎样统一判断导航接纳、已经发生的业务动作、可撤回的页面变化 |
| Host 了解整个模型请求的预算和其他来源 | 整轮不合预算与单 App 开页被拒发生在不同边界，作者不能用一项 JSON 限额推断整轮能否发送 |

**我建议此刻只改善解释。** 在已有作者说明中给“容量拒绝”配一对正反例，标明哪些结果保证恢复、哪些要查看投影健康和实际业务结果。保留首次失败的错误与位置，方便 Agent 区分“换小一点的内容”与“先修复应用的投影”。这样能减少当前误用，又不预先规定旧页应当总能使用，也不替业务写入安排自动补偿。

**什么时候值得恢复讨论。** 当你决定重新讨论开页时，用相同的失败用例逐项核实业务动作是否发生、候选是否接纳、原页是否仍可操作，以及下一次成功观察应呈现什么。两种作者方式都能给出可验证的回答，再讨论 API。此前 03 的装配收拢、06 的提交桥和 12 的性能工作都应把当前差异作为回归边界。本文不给开页事务或恢复状态机排实施顺序。[议题 10](10-opening-deferred.md)

## 11 · 展示 Ref 和调用 Ref 分别需要哪些信息

**我的判断。** 保留两种格式是已经确定的产品设计。阅读页面时，Agent 需要一个就地可读的标签和类型。调用工具时，Runtime 需要知道数据来自哪一页。一个地址在这两个位置承载的信息原本就不同。统一格式的建议已经撤回，作者体验仍有很大改进空间。

把两个列表同时打开，例子最清楚。`files` 和 `search` 都在本页展示 `[测试文件](File:results[0])`。模型想让 `editor` 处理从搜索页看到的结果，可以提交下面这组参数。

```json
{
  "view_id": "editor",
  "target": "search.results[0]"
}
```

**这个设计的收益。** 每个列表只给自己的条目取局部名，不必申请全局 ID。模型从标签知道这是 File，从外壳知道来源是 `search`，从工具说明知道目标页是 `editor`。Runtime 在原观察内查已授予的值，再核对来源页的挂载和目标 Schema。列表重新排序后，第零项仍按原观察解析。App 最后判断该文件现在能否处理。Ref 只读让观察值有明确含义，同时保留应用合法更新底层业务的能力。

**它付出的成本。** 模型要把“展示类型 + 局部名”转换成“来源页 + 局部名”。跨页时容易错把接收页写在前缀里。更微妙的是，如果 `editor` 恰好也发布了同类型、同名的 `results[0]`，这个错地址可能完全合法，Runtime 的类型检查无法识别模型的意图。给 Core 增加更强的字符串检查也无法排除这种错误。作者应提供能区分来源和对象的业务标签，模型侧提示应选一个接收页与来源页不同的例子，让前缀的意义一眼可见。

**另一个容易忽略的边界是“画出来”与“发布出来”。** `captureRefEntries` 会捕获整个数组及其元素，正文调用几次 formatter 只决定呈现多少标记。若 App 捕获了一百项、仅画前十项，且观察策略授予整组 Ref，工具仍可能选择整个数组。作者若只打算提供本页十项，就先切出十项，再把这十项传给 `arrayRef`。这同时改善可选择范围和成本，也避免让 Runtime 解析正文来倒推授予范围。[Ref 捕获与格式化](../../sdk/src/app-factory/refs.ts) · [观察授权目录](../../runtime/src/core/invocation/observation-registry.ts)

**我的改进建议与验收。** 继续让唯一 formatter 处理类型、下标与标签转义，08 的新写法若采用也复用它。用上面的双列表场景，把选中来源页、整数组、数组元素、多选重复与可选缺省一起验证。再传一个普通路径 `dir/test.txt`，确认它按普通业务字符串进入 handler。View id 与 Ref 局部名所受的点号限制只适用于地址组成部分。未来若确有字段读取或 Agent 自建变量需求，应另论其作用域和生命周期，当前协议已能解决本文的问题。[议题 11](11-ref-address-contract.md) · [显式 Ref 的解析与类型校验](../../runtime/src/core/tool/snapshot-value-arguments.ts)

## 12 · 完整快照要保留，重复工作可以逐项减少

**我的判断。** 一个 IDE 同时打开列表、编辑器、搜索页，改一个字符后，下一次成功观察仍须包含这三页。调用者依赖的是“我拿到了完整工作现场”。至于内存里是否真的复制了三份正文、跨 Worker 发送多少字节、最终请求消耗多少 token，是三笔不同的账。文章的最大优点就是把这三笔账分开，也给出了可以停止优化的条件。

**现在已有哪种证据。** 原文在 Node v23.11.0、合成多页字符串的纯 Core 微基准上取五次中位数。512 KiB 输入时，prepare 为 16.005 ms，publish 为 15.049 ms，单独计算诊断 FNV 为 10.202 ms。三个数字分别测得，不能相加成一次请求的耗时。样例没有经过 Preact、Worker 和模型，原生 SHA 的对照也只提示如何找热点。这些是原文的历史数据，本次没有重跑或据此估算模型成本。[议题 12 与复现方法](12-snapshot-performance.md)

**我会把首项优化再缩小一步。** 当前 `validatePreparedSnapshot` 在成功返回前计算诊断摘要，准备端实际取出的是草稿和规范化内容，Store 又在验证完成后才用规范化内容判断是否相同。另一方面，已发布 `AppSnapshot` 确实公开 `contentDigest`，并有测试验证其值。优先尝试省掉准备端和未变化分支中无人使用的摘要计算，同时保持真实读取者得到相同结果。在改哈希算法、放松校验或引入新句柄之前，就能单独测量这个变化。[快照校验](../../runtime/src/core/snapshot/validate-snapshot.ts) · [Store 的判等与发布](../../runtime/src/core/snapshot/store.ts) · [摘要合同测试](../../runtime/src/core/snapshot/validator.metadata-boundary.test.ts)

**各项候选解决不同的瓶颈。**

| 候选 | 它能省什么 | 应先取得的证据及保留的责任 |
| --- | --- | --- |
| 在同一所有者内复用已验证候选 | 重复拷贝、重复展开相同值 | 证明数据由本端独占且不可变，明确何时结算和释放。公共输入与 Worker 接收端继续核实来源、结构和顺序 |
| 页级结构共享 | 新旧完整快照可引用未变的页面记录，减小分配和持有量 | 测单页更新与长期持有旧观察。仅正文相同仍要提交 Ref、启用状态和实时 handler 的变化 |
| ArrayRef 捕获一次，元素引用原数组内的索引 | 整数组和逐项捕获的重复数据 | 检查旧观察经重排仍取到旧元素，整数组及元素的授权、逻辑计数与限额保持各自含义 |
| 跨 Worker 增量传输 | 接收方已有基线时少传字节 | 先证明确实慢在传输。基线确认、乱序或缺失、重同步和实例退出都增加长期协议责任 |

**我不同意把 P0 至 P3 读作一个必须走完的路线图。** 两端有两次验证，有时是因为数据刚跨过真实的所有权边界。发送侧打过标记，不能代接收侧判断实例和来源。即使私有 WeakMap 能证明句柄来自本域，也无法自行限制候选总字节或在关闭时了结在途持有。当前 Worker 刷新请求可以发送完整草稿，因而同域共享带来的收益到通道还有一道边界。共享内存更会让原本独占的不可变数据变成多个写者可接触的字节。若只是诊断 hash 慢，承担这些成本得不偿失。[Worker 全帧发送](../../runtime/src/worker-runtime/index.ts) · [诊断哈希实现](../../runtime/src/core/snapshot/json.ts)

**我会怎样测、何时停。** 固定同一版本和页面内容，分别比较“完全未变”“一页改一字”“正文相同但 Ref 或 enabled 改变”“大 ArrayRef 重排且旧调用尚在途”。记录准备与观察时延的中位数及高分位、捕获次数和字节、跨 Worker 字节、旧观察释放前后的持有量，再单独记实际模型输入量。若局部调整已消掉可见热点，完整帧继续作为默认传输。若真正昂贵的是模型输入，优先回到 App 的分页、正文范围和 Host 的请求预算。内存里共享了一页，并不会使模型请求少包含那一页。

## 把十二篇放在一起，哪些决定值得先做

AOTUI 对持续操作一个工作现场的任务最有价值。一次性查个数，工具直接返回答案就能完成。若要同时打开几个对象、比较、修改，再回来确认结果，传统的长工具回包会将当前事实埋进多轮记录。AOTUI 给当前页面保留可定位的位置，并让同类页面共享操作。它能否像 Linux 的系统调用或 Web 的页面标准那样被反复采用，取决于第三方能否在不熟悉内核细节的情况下获得同一行为。类比能帮助选择要稳定的边界，不能代替生态采用证据。

| 设计层次 | 我认为最该稳定的东西 | 第一项值得投入的工作 |
| --- | --- | --- |
| 概念设计 | 页面是可切换内容的工作场所，Ref 来自原观察，实时业务判断归 App | 把“修改当前页面”和“修改刚才选中的对象”放进同一作者样例，让错误目标显形 |
| 系统设计 | 执行端按 App 实例提交，Host 按实例采用观察。Runtime 维护资格并承担共用装配，Host 负责实际发出的请求 | 先用第二个最小宿主验证 03 的装配负担，再沿 05 保留一份原产物作升级基准 |
| 模块设计 | SDK 承担作者表达、渲染提交和引用捕获。Core 处理已提交数据、来源资格和调用。执行后端证明交付与退出 | 先划清 Preact 时序、Markdown 正文、XML 外壳的消费者与错误归属，再决定具体目录和包 |
| 机制设计 | 页面、Ref、工具同源，业务结果与呈现结果分开，优化保留原观察及在途责任 | 优先检验 09 的模型参数提示和 07 的可解析性。12 的优化从可以测量、此次提交又用不到的诊断计算开始 |

**如果只选一个下一步，我选 03，但验收它要借 01 的真实请求和 05 的真实产物。** 用已有 SDK 构建一个带列表和详情页的 App，用默认托管路径作参照，让一个通过公开 Core 入口接入的小 Host 从开页走到请求、调用、查收据和关闭。记录作者必须导入哪些入口、宿主必须亲自维持哪些顺序，再看现有 AppKernel 和 interaction 可以替它们承担哪几项。保留这份应用产物，就有了以后内部升级的对照物。这个做法可以同时检验三项判断，只需一份应用，也不会先承诺第二个执行后端。

**两种 Agent 需要两份证据。** 测使用者时，给模型两个分别发布同名 Ref 的列表页、一个可切换详情页和一次外部变化，观察是否选中正确对象、是否重复写入，以及恢复用了几轮。测开发者时，只给它发布包、公开类型和 README，让它完成同一行为，记录首次构建、错误后修复轮次、实际私有依赖。二者都应保存真实请求和运行结果，并固定模型、任务及依赖版本作可比对照。工程用例能验证基础行为，无法回答哪种作者 API 更好学、CLI 是否更省 token 这两个产品问题。

## 全文复核及证据边界

**一致性。** 逐篇回查后，我保留了以下几组看似相反、实则属于不同责任的结论。

- **01、02 与 11**　替换当前页不会改写已发出的输入。原 Ref 仍是旧值，handler 仍使用当前有效页面。两页都有同名局部 Ref 时，模型必须选对来源，App 仍须核实业务目标。
- **03、04 与 12**　可以收拢同一侧重复的装配或复制。跨 Worker 的来源检查、采用资格和真正的资源退出各有独立证据，不能靠共用一个对象或命中缓存省略。
- **06、07、08 与 09**　同一提交内的正文、Ref、能力要配套。改变声明位置、正文转换或模型提示时，应让各层继续消费同一次捕获与同一份参数声明。Ref 的展示和调用双格式、普通业务参数与执行端校验均有既定用途。
- **01、10 与 12**　成功观察完整呈现所有已开页。投影额度、全请求 token 预算和失败后的导航恢复各有边界。开页重设计继续暂缓，性能优化不替它选方案。

**长期主义。** 01、02、11 的产品定义已确认。05、08、09 获认同的是方向。03、04、06、07、12 的具体方案仍待讨论，10 明确暂缓。是否采取 Breaking Change，要同时说出它解除的依赖、受影响的消费者和验证旧行为的办法。已有证据足以指出公开类型、错误提示、呈现边界的问题，跨版本 App 兼容还要证明原样保留的旧产物能在所承诺的新 Runtime 上工作。

**Minimalist。** 作者误用，先改善诊断和示例。集成负担重，先让现有对象接手那些反复需要维护的规则。性能有热点，先避开重复且结果未被使用的计算。只有这些办法遇到可复现的上限，再考虑 descriptor 新 API、独立包、替代后端、AST 或增量协议。反过来，删掉错误反馈、原来源持有或执行前复查，会将正确性成本转嫁给所有 App，即使源码缩短也不算简化。[项目 minimalist 准则](../../.agents/skills/minimalist/SKILL.md)

**本次证据。** 除逐篇阅读及源码核对外，使用本机 Node v24.15.0 对照了两个现有用例集，并针对四个边界执行了小实验。初次构造独立 Core 探针时漏传必需的 `now`，配置校验在初始化时拒绝。补齐后重新执行，以下是有效结果。
