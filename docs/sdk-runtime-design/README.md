## 这组文档要支持同一个长期目标

**让 Agent 容易使用 AOTUI App，也容易用 SDK 写出正确 App；让不同宿主复用稳定的交互语义，同时保留一个简单、强大、稳定的内核。**

用户以 Linux / shell、Chromium / HTML + JS + CSS 类比 Infra，本文据此关注“应用与宿主之间哪些合同应长期可靠”，而不把类比理解成要复制这些系统的规模。一个组件、类型、包或机制是否值得存在，必须回到它解决的真实边界问题。

正文沿用“具体例子 → 问题与责任 → 方案优劣 → 推荐和触发条件 → 验收与讨论记录”的顺序。接管首批的详细论证在 03，请求证据在 01，后端提示在 04，原样产物与复验入口在 05。

已确认概念的文档比较兼容该概念的实现或作者方式，不重新投票决定概念；暂缓议题只比较当前怎样管理这项未定工作，不展开其状态机。其余方案仍待讨论。

## 已确认的共同前提

1. AOTUI Messages 同时表达外部事实与 Agent 对这些事实的记忆；Agent 只能进行有限操作。
2. 一个 View 实例对应 GUI 网站或桌面应用的一个页面，可以展示多个对象并合法切换内容。
3. Ref 展示格式与调用地址保持分离；作者体验与性能改进必须保留现有 Ref 能力。
4. 开页准入与恢复的具体设计暂缓。
5. 核心保持简单、强大、稳定；业务状态、权限、冲突与业务补偿由 App 负责。

以上只作索引摘要，规范讨论分别归 01、02、10、11；后续更改必须更新对应原文，避免本索引形成另一套细节规范。

## 贯穿十二篇的 IDE 场景

这组例子使用相同页面与术语。它们不是要求所有 App 都采用 IDE 模型，也不冻结新的工具名称或 API。

| 阶段 | 应用与 Agent 发生什么 | 用来检验什么 |
| --- | --- | --- |
| 只有文件列表 | `files` 是 FileList 页面，显示文件与 `results` ArrayRef；没有 FileDetail 页时，不暴露相应编辑能力 | 动态工具以页面类型及实例条件为基础，工具定义按 App + ViewType 共享 |
| 打开 test.txt | `editor` 是 FileDetail 页面；工具返回操作收据，文件正文进入 XML + Markdown 的 View User Message | Tool 与 View 分担操作和状态呈现；不是两份独立业务数据真相 |
| 引用列表中的文件 | 展示为 `[测试文件](File:results[0])`；声明为 Ref 的调用参数使用 `files.results[0]`，接收页面可为 `view_id: editor` | 展示地址与调用地址不同，接收页和来源页也独立；仍限于同一 App 实例与原 Observation |
| 生成期间外部变化 | 模型看过版本 7，磁盘可能已经变成版本 8；当前这次输入不会自动更新 | 原观察值与当前业务状态分别负责；冲突、归属与权限由 App 判断 |
| 页内切换文件 | 同一个 `editor` 从 test.txt 切到 notes.txt | View 是页面，不是永久业务对象；具体操作目标由业务参数与页面语义表达 |
| 再次呈现 | 当前投影中 editor 只有一个最新快照；其他页面没有变化也必须完整呈现 | 完整快照语义、局部计算复用、原观察持有可以同时成立 |

`results` 中是否含文件版本、业务 ID 或其他字段，由 App 的业务需要决定。它们不是 Runtime 新增的文件协议。例子中的正常开页也不预设 [10](10-opening-deferred.md) 暂缓的准入、回滚或恢复机制。

## 长期主义与 Minimalist：用同一把尺子比较方案

先检查硬约束，再比较成本与收益。违反已确认约束的选项直接说明为何排除，不用“更少代码”抵消语义损失；满足约束的方案则不因为抽象更多、依赖更成熟或名字更通用而自动胜出。

| 比较维度 | 必须回答的问题 | 在这组文档中的具体含义 |
| --- | --- | --- |
| 目标与语义 | Agent 能否正确看见、选择和执行？ | Messages 同时是事实与记忆；输入冻结；动态工具、Ref 原观察与双格式保留 |
| 责任与状态 | 谁拥有状态，谁作权威判断，是否重复保存同一事实？ | 业务状态归 App；提交、观察资格、物理资源分别由对应 owner 管理；减少重复 owner，不删除真实边界校验 |
| Agent 使用与开发成本 | 使用者是否少抄对象 ID、少猜当前状态？作者是否少接内部协议、少维护重复 Schema？ | 同时衡量生成正确 App 的难度、诊断与修复路径，不能只看 API 字符数 |
| 长期演进成本 | 哪些类型、语法、产物和行为会成为兼容承诺？ | 稳定 App 合同；把 Preact 内部、DOM、Worker 与模型别名限制留在相应适配边界 |
| 当前必要性 | 现在有哪些真实消费者、重复代码或可复现问题？ | 先复用、标准库、平台和现有依赖；没有需求的调度、事务、DSL、通用策略系统暂不引入 |
| 证据与退出条件 | 如何证明收益，什么条件成立才升级下一步？ | 架构以真实消费者与所有权验证；性能以分阶段测量；成熟实践不等于本项目已有可直接替换的库 |

方案表用于在实际责任之间作取舍。保持现有语义与公共合同的内部整理，可在已有授权范围内实施。改变产品语义、公共 API 或兼容承诺的提案，经用户决定后再迁移。

## 各文档共同遵守的职责边界

以下按责任组织，名称和物理包边界仍以各议题状态为准；尤其 `AppExecutionSession`、显式 bridge、descriptor 与独立合同包都是候选设计，不是现有新 API。

| 责任 | 唯一权威内容 | 不向该层转移什么 | 主要议题 |
| --- | --- | --- | --- |
| App | 业务状态、页面意图、目标归属、外部版本、权限和业务恢复 | 不接管其他来源 Messages，不重复实现框架观察资格 | 01、02 |
| 作者适配 | Preact / 普通 TypeScript 表达、Ref 声明与捕获、DOM 到正文、真实提交桥 | 不从正文猜工具与身份，不维护另一套当前业务真相 | 06、07、08、11 |
| 执行端公共装配 | 当前 App 实例、页面和工具绑定、投影生产与应用清理 | 不兼任调用端 Observation 数据库或物理 Worker 管理器 | 03、04 |
| 调用端交互 Core | 已接收投影、Observation 采用与资格、Ref 来源、收据和必要持有 | 不猜业务闭包含义，不因后台发布宣称模型已读 | 01、03、12 |
| 执行后端 | 加载、通信交付、断连、物理资源和实际退出 | 不把超时说成未执行，不把同进程关闭说成强制终止 | 04 |
| 模型表示与 Host 集成 | XML / Markdown 外壳、模型 Schema 与别名、请求组装与总预算 | 不另建业务身份或授权；不静默隐藏已打开页面来腾空间 | 01、07、09 |

05 约束上述跨边界承诺的稳定范围，12 约束优化必须保留的语义。默认 Preact、可信 Node Worker、单 Agent 独占实例与串行调用主路径保持原有目标；不由解耦讨论自动引入多 Agent 调度、远程执行平台或更强安全沙箱。

**首批从 03 开始**，因为一次装配顺序出错就可能让使用 App 的 Agent 操作错误的页面。SDK 已经让作者可以只描述业务。默认 Host 代为承担整帧接纳，独立 Host 仍需亲自接线。第一批消除了仓内两处组帧顺序的差异，并量出了独立消费要承担的责任。[所有权与方案](03-core-assembly.md)

**装配路线取决于一个产品选择。** 第三方在默认 Worker 之外直接托管 SDK factory，是否属于近期正式支持范围？建议暂按现有默认托管与高级 Core 提供支持，等具体 Host 能说清愿意拥有哪段生命周期，再选窄组帧入口或整段托管。XML 字符策略、公开 `entity` 和全面限定别名各有自己的消费者与代价，可独立讨论。[后端范围](04-execution-backend.md) · [发行边界](05-compatibility-and-distribution.md)

## 分批实施与验收

**第二批已验收。** 接收端 Store 同时知道内容是否相同、是否有容量、是否真正生成新快照，因此由它在新快照上计算公开摘要。准备端和重复发布省去了无消费者的计算。512 KiB 正文重复发布的中位耗时从 8.995 降至 2.011 ms，变更发布从 9.046 到 8.964 ms。64 KiB 变更发布的 p95 从 1.190 到 1.609 ms。原样 Work Items 在本批构建的 Runtime 上通过双路径验收。[三档负载、持有探针与兼容范围](12-snapshot-performance.md)

**第三批已验收。** SDK 诊断能指引作者把错放的 Ref hook 移进页面子组件。现有模型 Schema 生成器使用 Ref 声明里的类型和值形状。在同一组真实请求中，四种选择可区分，完整请求体从 14,949 到 14,912 字节。相同的两个错误选择仍在业务执行前被拒，随后正确调用成功。开发复测为 222 项 Runtime、46 项 SDK 与 8 步隔离包消费。负责人独立复跑其中 123 项、改前和改后的 Ref 包消费，以及原样 Work Items 双路径。测试使用预定的模型响应；作者修复练习已知错误位置。[作者修复](08-ref-authoring-scope.md) · [工具参数、容量与恢复](09-schema-and-tool-naming.md)

## 一致的推进思路，不是一揽子实施清单

1. **先固定已有语义和责任。** 01 / 02 / 11 的用户决定优先；03 先找出实际装配 owner，05 再说明哪些边界值得稳定。不能一边减少 owner，一边在别的议题新增同义注册表。
2. **先复用当前实现来改善边界。** 04 沿用默认 Node Worker，06 在现有提交桥保留真实错误原因。07 在现有 visitor 修复词界，模块迁移仍取决于消费者。08、11 共用页面 Ref 的捕获与呈现，09 从同一声明生成模型参数提示。
3. **用证据决定新增机制。** 03 的更大公共装配必须真实拥有资源与状态，05 的拆包必须解决依赖与分发，08 的新作者写法必须降低实际出错成本，12 的 delta / transfer 必须有跨边界测量支持。
4. **维持范围边界。** 10 继续暂缓；默认作者技术、Tool 与 CLI 的表面选择、通用记忆或业务数据库都不因本次修订被重新决定。所有候选在用户选定前继续标为待讨论。

跨文档检查最容易出错的三件事：缓存正文不等于冻结实时 handler；共享 Ref 值不等于共享调用资格；同一语义合同不等于每个环境的依赖和故障都相同。03–09 的模块调整与 12 的优化都必须同时满足这些限制。

## 状态约定

| 标记 | 含义 |
| --- | --- |
| 已确认 | 用户明确确认的产品定义、约束或决定 |
| 方向已确认，方案待讨论 | 用户认同问题/方向，具体 API、模块或实现尚未确定 |
| 待讨论 | 研究结论或推荐方案，可在后续讨论中修改、替换或撤回 |
| 暂缓 | 保留事实与问题，不继续展开设计或列入当前实施项 |
| 已撤回 | 历史建议不再有效，保留简短理由避免重新引入 |
| 已实现 | 有实现、受影响的消费者、必要验证与文档可查。仅限明确标注的部分 |

代码事实、外部成熟实践和本项目提议分别标识。伪代码仅说明边界，不构成可直接调用的现有 API。

## 每次讨论后的更新规则

1. 在对应议题正文直接修改当前结论、方案或未决问题；不在新的同名文件中建立第二份正文。
2. 关键变化追加简短决策记录：日期、用户澄清或证据、结论、状态、取代了哪条旧建议。
3. 明确区分“认可方向”“选定方案”“授权实现”“已实现”；不能因为用户没有反对，就把推荐方案改为 accepted。
4. 修改跨议题前提时，同步检查关联文档，特别是页面语义、Ref 双格式、真实提交、来源与持有语义。
5. 实施时在对应文档补充迁移落点和实际验证；只把已生效的合同摘要同步到 AGENTS.md 与 SDK/Runtime README，详细推理继续留在本目录。
6. 更新文档基线与修订记录，保留 Git 历史。下载包或聊天中的副本仅是某次修订的阅读副本，后续以仓库本目录为准。

阅读副本保留仓库相对源码链接；查验源码时应在仓库的对应目录打开。ZIP 内采用 `docs/sdk-runtime-design/` 路径，可与项目目录结构对应，不另建第二份权威设计目录。
