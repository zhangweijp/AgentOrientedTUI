## 结论

**AOTUI 的一个 View 实例，对应 GUI 网站或桌面应用中的一个页面。页面可以包含多个业务对象，也可以在自身生命周期内切换内容、筛选条件或当前对象。**

上一轮建议“一个 View 实例必须始终对应同一个业务对象”过于收紧，应撤回。它可以是特定应用的一种设计方式，不能上升为 Runtime 的通用要求。

## 用户明确约束

> AOTUI 的一个 View 实例 对应的 就是 GUI 网站内/桌面应用的一个页面

## 先看一个例子：同一个编辑页，今天显示谁

一个 IDE 有两个页面：

- `files`：FileList 类型，列出 `test.txt` 和 `notes.txt`，发布 `results` ArrayRef。
- `editor`：FileDetail 类型，先显示 `test.txt`，用户操作或应用逻辑也可以让它切到 `notes.txt`。

Agent 在观察 O1 中看到的是 `test.txt`。模型生成期间，`editor` 切到了 `notes.txt`，但还是原来那一个页面。此时，“切换编辑器的显示模式”与“修改我刚才选中的 test.txt”明显不是同一类意图：前者作用于当前页面，后者需要确定业务文件。

如果把 View 身份强行定义为文件身份，框架就必须要求所有页内切换都关闭重开；文件列表、搜索结果、包含多个对象的工作台也会变得难以解释。如果反过来认为 `view_id=editor` 已经永久确定了 `test.txt`，又会错误地把页面路由当成文件选择。

正确的区分是：**页面回答“到哪里操作”，业务参数或 Ref 回答“对什么操作”，App 回答“现在是否允许这样操作”。** 页面、参数和权限可以相关，但不能互相代替。

本文的页面和工具名称用于贯穿例子，不新增固定页面类型或工具签名。此例假设页面已正常打开，不涉及 [10](10-opening-deferred.md) 暂缓的准入与回滚设计。

## 页面身份与页面内容应当分开

| 概念 | 例子 | 变化是否一定需要新 View 实例 |
| --- | --- | --- |
| 页面实例 | 一个 IDE 编辑页、一个订单列表页 | 实际关闭后重新创建，应是新实例 |
| 页面类型 | FileDetail、OrderList | 类型用于共享工具定义 |
| 页面内容 | 文件正文、订单集合、搜索结果 | 不需要 |
| 页面内状态 | 筛选条件、排序、当前选项、进度 | 不需要 |
| 页面当前展示对象 | 同一详情页面从 A 切换到 B | 由 App 页面语义决定，不能一律强制重建 |

同类型多个页面共享一组 Tool Schema，但各有自己的 context 和局部状态。这与页面模型一致。

## 当前 Runtime 实际保障什么

当前 `createViewOwnedTools()` 通过页面 owner、类型和工具激活，维护页面实例与操作资格。同一 owner/type 的连续页面可以保留 `viewInstanceId`；工具持续启用可以保留 `activationId`，而其 execute/context 绑定可以更新。

它提供的是：

- 不把已关闭页面的旧调用重定向给同名新实例；
- 同类型另一页面仍打开，不代表被关闭页面仍可执行；
- Ref 从原 Observation 解析，不能暗换为最新值；
- handler 使用符合当前绑定的页面状态、函数与服务。

这些保证不等于冻结页面全部内容，也不等于冻结任意业务闭包。证据见 [view-owned-tools.ts](../../runtime/src/core/tool/view-owned-tools.ts) 的 `prepareFrame()` 与 `invokeTypeTool()`，以及 [Runtime README](../../runtime/README.md) 的来源绑定说明。

## 如何解释“旧观察中的操作作用于当前页面”

假设一个详情页面在模型生成期间由对象 A 切换为 B。旧观察的页面调用还能否执行、应操作谁，取决于操作本身的业务语义。

### 操作页面当前状态

“把当前筛选条件清空”“切到下一个结果”等操作，本来就可能针对页面的当前状态。Runtime 不应强迫这些操作带某个永久业务对象 ID。

### 操作观察中选中的对象

“删除刚才看到的订单”需要明确目标。App 可以通过 Ref 接受原观察对象，再检查对象当前存在性、所属关系与业务前置条件。此处 Ref 提供旧观察值，不提供永久权限，也不保证外部对象仍然没有变化。

对应 IDE，若某个操作声明接收一个文件 Ref，可以在同一 App、同一原 Observation 中使用如下输入示意：

```json
{
  "view_id": "editor",
  "target": "files.results[0]"
}
```

`editor` 选接收页面，`files.results[0]` 选原观察中的文件值；后者在 `files` 正文显示为 `[测试文件](File:results[0])`。这两种地址并不统一。App 可以允许编辑页处理所选文件，也可以要求目标必须等于当前文件并拒绝不匹配；Runtime 不擅自选择其中一种业务规则。

### App 需要切换时撤销旧页面操作

某个应用可以选择在特定导航后创建新 View handle/key，或改变相应能力的有效性。这是应用表达生命周期的一种方式，不是所有页面都必须遵循的映射。

**SDK 的任务是让以上选择表达清楚；Runtime 的任务是准确执行声明的实例与能力语义。**不通过分析“文件”“订单”等业务含义替应用猜测。

### 接收页面合法，不代表模型一定表达了正确意图

[Review 02](REVIEW-2026-11-18.md#review-02) 对已有例子的补充值得保留：若工具只接收 `replacement`，业务语义又明确是“修改执行时的当前文件”，那么页面从 A 切到 B 后，原观察发来的调用可能在所有框架检查都通过的情况下修改 B。调用来源正确、页面仍有效，与模型是否选对了业务目标是不同判断。

因此作者示例应并排给出“切换当前页面显示模式”和“修改观察中选中的文件”两个操作。后者若依赖所见版本，应在实际业务写入边界使用可提供的版本条件；先读一次版本、再无条件写入，仍可能在两步之间遇到外部变化。SDK 不承诺替文件系统实现它没有提供的原子更新能力，也不把全部页面操作都强制改成对象操作。

该补充强化了现有分工，不引入工具类别或业务冲突管理器。Review 中报告的旧 Ref / 当前 handler 实验与本页语义一致；本轮按源码核查其机制，没有把该报告的运行结果重新标为本轮测试通过。

## 三种页面组织方案：由应用按意图选择

这些是兼容同一 Runtime 的 App 设计方案，不要求整个生态选定唯一页面样式。方案 A 可以与 C 组合；它们分别优化页面组织和目标表达。

| 方案 | IDE 里的具体做法 | 优点 | 代价与风险 | 适用条件 |
| --- | --- | --- | --- | --- |
| A. 每个文件一个编辑页面 | `editor_test` 与 `editor_notes` 各自显示一个文件，工具定义仍按 FileDetail 共享 | 空间关系清楚；Agent 容易把页面与文件对应；各页面可有独立编辑状态 | 多页正文占用上下文；即使页面固定文件，外部版本冲突仍需 App 检查；不能把这种习惯写成内核约束 | 需要同时比较或维护几个文件的应用 |
| B. 复用一个页面，操作明确针对当前页面状态 | `editor` 切换文件；如“切换显示模式”“清空当前筛选”使用当前 context | 页面数量少；表达常见 GUI 导航；不增加新的身份机制 | “编辑当前文件”若在输入冻结期间切换目标，可能偏离 Agent 原意；需要明确业务语义和相应保护 | 操作本身就是页内交互，而非必须锁定所见业务对象 |
| C. 复用页面，敏感于目标的操作显式接收观察值 | `editor` 仍可切换；编辑某文件通过 `Ref<File>` 接受目标及 App 所需版本信息 | 同时保留灵活页面与明确目标；直接复用已有 Ref；Agent 无需抄业务内部 ID | Schema 多一个有意义的参数；App 需处理目标与当前页面不一致、外部版本变化等业务事实 | 操作应针对“刚才选中的对象”，特别是不能容忍目标歧义的操作 |

### 长期选择：稳定页面语义，允许应用选择交互方式

推荐 Core 继续只理解页面实例、类型、观察与能力，不增设通用“业务实体绑定器”。SDK 用并列例子说明 A/B/C，减少 Agent 作者把页面 ID 当业务 ID 的概率。对象指向敏感的操作可优先采用 C，但不把“所有参数必须 Ref 化”升级成新约束。

也不建议现在新建框架级“页面操作 / 对象操作”工具类别。上述区分用于解释作者意图，具体执行仍走同一套 Tool 与参数合同；它不是 `Mutating` 或 `effects` 一类分类的替代品。

从 Minimalist 看，当前已有页面身份、实例 context 和显式 Ref，足以表达这三种方式。先补上清晰示例和现有合同覆盖，只有多个真实应用反复写出相同且属于 SDK 的逻辑，才评估一个可选 helper。单纯担心未来导航复杂，不足以引入通用 Router、实体数据库或新的撤销系统。

| 上一轮表述 | 当前处理 |

## 对后续设计的影响

1. [03](03-core-assembly.md) 和 [04](04-execution-backend.md) 的实例装配不能引入“一个 View 等于一个实体”的默认假设。
2. [08](08-ref-authoring-scope.md) 改善的是页面内 Ref 的作者表达，不改页面的业务对象模型。
3. [12](12-snapshot-performance.md) 的缓存必须同时关注页面内容与当前绑定，不可把正文未变理解为 handler 未变。
4. 页内路由、URL/导航历史以及开页准入的完整设计留待讨论；本文件只固定页面概念。

## 验收例子

- 一个列表 View 展示多个对象，筛选后仍是同一页面，工具仍按该页面类型共享。
- 一个详情 View 合法切换当前对象，不因“业务 ID 变化”被框架强制关闭重开。
- 同一逻辑 id 的页面真正关闭重建后，旧调用仍被实例身份机制拒绝。
- 从旧观察传来的显式 Ref 仍得到原值，由 App 决定是否可在当前业务状态执行。
