## 结论

**由 AOTUI 产出的 Messages，既表达应用提供的外部事实，也是 Agent 对这些外部事实的记忆。Agent 通过 AOTUI 提供的有限操作改变这一部分记忆。**

不能将二者拆成互斥分类。上一轮强调“Runtime 不做通用记忆管理”，若被理解为否定这些 Messages 的记忆属性，需要在此纠正。

## 用户明确约束

> 由 AOTUI 产出的 Messages，既是外部事实 也是 Agent 对这些外部事实的记忆，Agent 只能对其进行有限的操作

这里的“有限操作”是产品能力边界：Agent 通过应用允许的打开、关闭、选择、刷新、编辑等操作，影响应用页面及其对应的上下文投影。它不自动获得任意改写所有 Messages 的权限。

## 先看一个例子：文件已经变了，Agent 为什么还“不知道”

IDE 已有 `files` 文件列表页面，Agent 从中打开 `test.txt`，得到 `editor` 页面。下面的版本号只是 App 用来检查文件变化的业务字段，不是新增 Runtime 协议。

| 步骤 | 外部文件与应用 | 本次模型输入中的记忆 | 预期行为 |
| --- | --- | --- | --- |
| 1. 观察 O1 被采用；随后模型请求实际携带 O1 | `test.txt` 版本 7，正文为 `Hello` | `editor` 的 User Message 显示 `Hello` | 编辑工具随 FileDetail 页面可用；Agent 据此思考 |
| 2. 模型仍在生成，外部程序改了文件 | 文件成为版本 8，正文为 `Hello world`；假设 IDE 已收到变化 | 已发送的 O1 仍是 `Hello` | 后台形成新投影不代表模型读过它 |
| 3. Agent 发起基于所见版本的编辑 | App 收到原观察中的目标值及当前业务状态 | 此时不能偷偷把输入改为版本 8 | App 自行检查版本，选择拒绝、合并或按明确业务规则执行 |
| 4. 下一次成功观察 O2 被采用；后续请求实际携带 O2 | 页面反映 App 已确认的最新状态 | 当前 `editor` 只出现一份最新快照 | Agent 这部分工作记忆随新输入更新 |

第 3 步可以使用显式 Ref 携带所见文件及版本；是否需要这个业务版本由 App 决定。Runtime 保证 Ref 来自 O1，不负责判断文件应该如何合并。若工具成功写入后页面生成失败，收据仍须保留真实写入结果，不能为了“补一份新记忆”再执行一次写入。

这里的难点不是选择“事实”或“记忆”中的一个名称，而是让**外部状态、应用投影、实际模型输入**保持可解释的关系。Message 是应用在某次观察时提供的事实，也是模型据以行动的记忆；它不自动成为实时订阅，也不是模型可以任意涂改的笔记。

“事实”具有来源与观察时点。AOTUI 不应把旧观察冒充外部世界此刻的全部状态，也不承诺应用提供的信息永远没有业务错误。

## 必须分别表达的五个时点

| 时点 | 发生的事实 | 不能由此直接推出 |
| --- | --- | --- |
| 外部业务变化 | 文件、任务等业务状态发生变化 | 模型已经知道变化 |
| 应用准备完整投影 | View、Ref、Tool 能力形成一致候选 | 该候选已进入模型输入 |
| 观察被采用 | 本实例的调用资格切换到该观察，旧资格被撤销 | 请求已经发出，或模型已经读到该观察 |
| 请求实际携带该观察发送 | Host 使用对应的 Messages、Tools 与别名映射 | 生成期间能感知后续变化；网络异常能证明模型没收到 |
| 工具完成或进入未知状态 | 操作取得某种执行结果 | 下一次页面一定能成功呈现 |

这些区分服务于“事实与记忆的对应关系”，并不否认 Messages 是记忆。

### 采用之后仍可能发送失败：复用现有机制处理

`adoptObservation` 与网络发送不是一个原子操作；多个 App 也分别采用。正确顺序已写在 [Runtime README](../../runtime/README.md) 的模型集成步骤中：先用同一组完整候选组装正文、Tools 和本轮别名映射，连同历史、指令、其他来源和预留输出检查实际请求预算，再检查每次采用结果，最后发送匹配的请求。采用后不能另换正文或工具，却沿用原调用来源。

| 失败位置 | 应采取的处理 | 不能声称什么 |
| --- | --- | --- |
| 预算检查失败，尚未采用 | 不发送；释放未采用候选，保留原已采用来源 | 保留来源不保证所有旧工具仍可调用，当前实例／激活检查仍在 |
| A2 采用成功，B2 采用失败 | 放弃尚未发送的组合；结算无用候选；重新准备时重新组装并检查预算 | 不能回滚已撤销的 A1 资格，也不能发送包含不可用 B2 的旧请求 |
| 采用成功，发送随后失败 | 明确本轮继续等待还是已经终止；原轮仍可能返回时保持原来源，已放弃的返回不能再分派工具；新轮重新准备 | 不能因 send 抛错就宣称模型一定没收到，也不能把采用撤回成旧资格 |

这里不是要求新建事务层。现有 [Source adapter](../../agent-driver-adapter/src/semantic-aotui-driven-source.ts) 已显式报告 `SEMANTIC_ADOPTION_PARTIAL`：部分成功时关闭不能继续使用的旧组合与本轮上下文，保留各 App 的采用结果；[对应测试](../../agent-driver-adapter/src/semantic-aotui-driven-source.test.ts) 区分了全失败保留有效旧上下文与部分失败收尾。因此，“主动释放 B2 后分别采用 A、B”的纯 Core 探针只能说明局部语义不组成全局事务，不能证明默认 Host 发错请求，或描述 adapter 收尾后仍保留 B1 的状态。

配置预算时，Driver 在 provider 的调用参数上检查输入，再调用采用钩子。主循环在本轮结束时释放上下文。已有模型替身用例覆盖采用失败，本轮把这一路径与两个真实 App 实例连在一起。[Driver 请求边界](../../agent-driver-v2/src/core/llm-client.ts) · [主循环](../../agent-driver-v2/src/core/agent-driver-v2.ts) · [既有采用测试](../../agent-driver-v2/tests/core/context-adoption.test.ts)

### 从预算检查一直看到 HTTP 请求

在同一 Desktop 清单里放入两个 Work Items 实例，一个由默认 Worker 托管，另一个通过纯 Core 装配。Source 实际生成 User Messages、工具 Schema 与别名路由。Driver 汇入一条独立历史来源和内置指令，交给安装包中的 AI SDK 与 OpenAI 兼容 provider。测试只在最终 HTTP 传输边界记录请求并回复预设的 SSE，不从 Source 预览反推模型收到了什么。[贯通用例](../../sdk/tests/fixtures/assembly-consumer.mjs)

| 按执行顺序观察 | 本轮实际参数与结果 |
| --- | --- |
| 预算拒绝 | 窗口 1,024，预留输出 256，输入上限 768。Driver 在 provider 参数上计得 18,246 个 UTF-8 字节，另加 1,057 余量，返回 `MODEL_INPUT_BUDGET_EXCEEDED`。本轮零采用、零发送。两个实例均能用先前已采用的观察再调用一次 `count` |
| 首轮发送，操作后再观察 | 两次请求各有 9 条 Messages、9 个 Tools，`max_tokens` 均为 256。每轮把候选正文、独立历史、完整工具参数 Schema 与 HTTP 正文逐项核对。对 11 个业务调用还核对 provider 别名、参数、App、语义 tool ID 与原 observation ID。首次正文显示 0 次检查，下次正文显示 1 次以及重排前选中的值 |
| 两个 App 部分采用 | 让第二个实例在采用前释放本轮候选。第一个 `adopted`，第二个 `rejected`，错误为 `SEMANTIC_ADOPTION_PARTIAL`。Driver 没有发出请求，收尾后两个本轮候选均不能再采用。重新取观察成功发送 8 条 Messages、9 个 Tools |
| 关闭托管 App 后发送 | 最后一次请求含 6 条 Messages、6 个 Tools。被关闭实例的页面和业务工具均消失，另一个 App 的工具和 Desktop 控制仍在。四次实际 HTTP 请求均发生在当轮全部所需观察成功采用之后 |

预算数字采用 Driver 的保守字节估算。测试同时保存实际 HTTP 正文；例如首次成功发送的正文为 18,189 字节，两种数字来自不同的序列化边界。当前数据可证明何时拒绝、何时发送和内容是否同源。真实模型的 tokenizer 计费、已采用后网络中断的送达状态、Agent 的选错率，仍需各自在对应边界取证。[安装包检查入口](../../sdk/tests/package-consumer/verify-package-consumer.mjs)

### 已发送的轮次如何收尾

第五批用原样 Work Items 的 Worker App，让模型请求先走完预算、观察采用和实际 POST，再由脚本控制 HTTP 回包。每次实际请求的 Messages、Tools 和别名核对到当轮 Source，预留输出为 256。一个列表页和一个仍有效的接收页足以区分下列事实。

| 实际发生的事件 | 确定的行为 |
| --- | --- |
| POST 已到达，Host 暂停，App 重排列表 | Desktop Host 的 pause 允许当前轮完成，保留下一轮的等待信号。新列表已发布，已发请求仍显示旧列表。合法回包在原观察读取 `items[0]` 的值 0，使用仍存活的接收页 `b` 与当前 App 状态。下一次成功观察显示重排后的列表及这次检查结果 |
| POST 已到达，Host 放弃会话 | 按默认 Desktop Host 的顺序 stop、dispose Driver、dispose Source、销毁 Desktop。随后送回完整工具调用，Driver 在响应出口截住它。实际记录为零调用、零正式助手响应、零工具结果。Source 已释放观察，Driver 在 `finally` 完成轮次清理 |
| 首次 POST 返回 503，传输重试后 SSE 读取出错 | 两次 POST 的正文逐字节相同，采用一次。Driver 收到明确读取错误，业务调用为零，本轮释放。随后的同输入触发被签名抑制，实际零采用、零发送 |
| SSE 送出可解析工具参数后直接 EOF | 旧包在通用 Chat Completions 和内置 DeepSeek 路径都执行一次。首版候选只在通用路径阻止调用。修正版两路均报告中断，观察释放，零分派、零业务收据，页面检查次数保持 1 |
| SSE 明确送出 `data: [DONE]`，省略 `finish_reason` | 在两条路径各自保持同一模型请求和工具片段，只追加一条跨块的独立 SSE 结束事件。旧包两路都执行一次，首版候选误拒通用路径，修正版两路均获一张成功收据，下一观察的检查次数升至 2 |
| 同会话得到新的合法输入 | 下一请求采用新观察，合法完整回包正常执行。对旧观察发起新调用时拒绝；以前的真实成功收据在 App 实例和保留范围内可按 `observationId` 与 `invocationId` 查得 |

App 负责发布内容、执行操作和判断业务前置条件。Host 指定暂停或销毁的方式，Driver 管本轮响应准入。这个 Host 在恢复时调用 `resume()`，销毁后重新创建会话；创建时的 `start()` 属于初始化。Source 把当轮别名映射到采用的观察，Core 在实际执行前仍检查资格、实例、激活、权限和原 Ref。测试中的重排是宿主用合法当前来源直接触发的 App 更新，观察新状态用于测量，采用新一轮仍发生在实际请求前。[Host 路由](../../host/src/core/session-manager-v3.ts)、[Driver 调用链](../../agent-driver-v2/src/core/agent-driver-v2.ts)、[Source](../../agent-driver-adapter/src/semantic-aotui-driven-source.ts)

首版候选只检查通用适配器的类和 AI SDK 返回的两个结束字段。实际安装的通用适配器和 DeepSeek 适配器在解析层都丢弃独立的 `[DONE]` 事件。上层看到的两种流可能同样是 `other` 且缺少原始原因。负责人据此退回首版，要求保住旧包可执行的显式结束响应，同时停止断流后的工具分派。

修正版在这两条 Chat Completions 路径的 provider fetch 边界读取 SSE 结束证据，按本轮实际请求尝试记录，再原样传送字节给原适配器。收到完整的独立 `[DONE]` 事件或显式 `finish_reason` 时，沿用正常分派路径。观测到裸 EOF 且仅有适配器合成的默认结束字段时，Driver 在产出正式助手消息和派发工具之前报告失败。原适配器的读取错误仍可见，轮次收尾沿用现有释放路径。Core 的旧来源资格、在途持有和真实收据查询有独立证据。传输重试只涉及模型请求，真实服务端的收单或计费须另行取证。[provider 路由与流观察](../../agent-driver-v2/src/core/provider-factory.ts) · [响应出口](../../agent-driver-v2/src/core/llm-client.ts) · [定点用例](../../agent-driver-v2/tests/core/tool-execution-owner.test.ts)

负责人独立复跑三份安装包的 12 组请求。每次待测请求有 6 条 Messages、6 个 Tools，预留输出 256。通用与 DeepSeek 路径的请求体分别为 14,702 和 14,724 字节，各路径在三个包间逐字节一致。298 字节的测试响应中已经有可解析的工具参数，追加完整的独立结束事件后是 312 字节。修正版只在第二种输入下对受测操作产生成功收据，App 的检查次数随之从 1 升到 2。该判断由 Driver 负责，结束事件之后仍须经过当前实例、接收页和原观察的调用校验。这里使用实际 provider 包和受控传输。[Driver 分派](../../agent-driver-v2/src/core/agent-driver-v2.ts) · [包兼容边界](05-compatibility-and-distribution.md)

## SDK 与 Runtime 的责任

- **SDK**：把应用页面、Refs 和工具绑定组织为一致投影，提供作者能够正确表达这些关系的入口。
- **Runtime**：维持投影与观察来源、实例身份、调用资格及必要数据持有；不把后台更新自动解释为模型已读。
- **App**：决定业务事实怎样呈现、哪些操作可用、业务写入与冲突如何处理。
- **上下文呈现边界**：按照既定 XML + Markdown 形式，把 View 包装为 User Message；应用只影响属于自身的投影。

本文不扩展 Host 设计。Messages 插入位置、跨来源排序和总模型预算，只记录为与外部集成合同有关的边界。

## 最新页面与旧来源的保留可以同时成立

“当前输入只保留一份最新 View”描述 Agent 可见的当前投影。

“在途调用仍持有旧 Snapshot”描述 Runtime 的执行责任。例如，已经分发的调用需要按照原 Observation 解析 Ref，必须继续持有对应值。采用新观察可以撤销旧观察的新调用资格，但不能伪造在途责任已经结束。

因此，不应以“删除旧记忆”为理由提前释放仍被执行责任使用的数据；也不应因为内核持有旧值，就把多个历史 View 都塞回当前上下文。

## 在已确认语义下，三种实现组织方式怎样取舍

以下比较的是**谁负责维护应用投影与观察的对应关系**，并不重新讨论 Messages 是否属于记忆。三种方式都必须满足 XML + Markdown / User Message、当前每页一份最新快照、有限操作和原观察绑定。

| 方案 | 如何完成上述例子 | 优点 | 代价与长期风险 | 适用判断 |
| --- | --- | --- | --- | --- |
| A. 各 App/集成者自己生成并替换所属 Message 片段 | App 输出页面，同时各自接线工具表、Refs、来源和替换规则 | 单一原型中接线直接；可以复用现成对话组装器 | 每个集成者都要证明页面与工具同源；若自己再维护一份“当前状态”，容易与 Runtime 分叉；Agent 作者必须理解宿主协议 | 可作受限适配方式；一旦仍由 Core 统一来源与资格，本质上就是 B 的薄适配，不宜提供第二套语义 |
| B. Runtime 管当前投影与观察，呈现层据此生成 Messages | App 提交一致页面；Runtime 关联来源；Host 在真实请求前采用对应观察 | 已有机制可复用；正确性集中证明一次；作者只描述应用，宿主只处理集成 | 需要清楚区分准备、采用与实际发送，不能承诺后台发布就是已读 | **推荐作为统一语义主路径**；03 改善装配体验，避免把内部步骤全部交给调用者 |
| C. 完整事件/快照历史作为主要存储，每次再物化当前输入 | 记录每次变化，从历史计算 O2，只把最新页面送入模型 | 在确有历史回放、审计需求的产品中有用；可追溯重建 | 引入日志保留、恢复、重放版本和数据迁移成本；不消除观察资格问题；并非实现受控工作记忆的必要条件 | 可在 Host/App 有真实历史需求时单独采用；不进入默认 Core，也不以历史替代原观察持有 |

“让 Agent 任意 CRUD 整个 Messages 数组”不在候选内，因为它越过了用户已经确认的权限边界。“自动把页面摘要成另一份长期记忆”也不能默认加入，因为摘要的事实保真、丢失信息和生命周期均需新的产品决定。

### 长期主义与 Minimalist 的共同结论

保留现有 Projection / Observation 分工，先消除多处装配和重复状态，不新建一个叫 MemoryManager 的权威实体。只有当前投影、有效观察与真实在途责任需要保留的值，才由该运行层持有；业务历史或审计日志应由有相应需求的层负责。

长期稳定的是“Agent 看过什么、这次调用依据什么、现在可执行什么”的合同；XML 排版、Messages 插入实现、内部缓存方式可以在各自边界演进。选择 B 不意味着把 Host 的完整对话历史、模型策略和业务数据库都放进 Runtime。

## 最小推进与可证明的结果

当前最小动作是统一作者说明和集成例子，复用既有观察与持有机制，并由 [03](03-core-assembly.md) 收拢容易接错的公共装配。没有独立需求时不新增记忆数据库、通用编辑器或后台摘要服务。

用前面的 `Hello → Hello world` 例子检查以下事实：

1. 后台发布后，已发送的 O1 不被标成“已经看见版本 8”；下一次真实请求才携带 O2。
2. 当前投影只含一份 `editor`，操作收据与必要旧来源不会因此被误删。
3. O1 的已分发调用保留原 Ref 值；O2 被采用后，O1 不能再发起新的调用。
4. App 的冲突结果与实际写入结果被忠实反馈，Runtime 不伪造业务回滚或自动重试。
5. 组合用例捕获最终请求，核对 O1/O2 正文、Tools 和 alias 同源；预算拒绝或部分采用失败不发送，发送失败不恢复旧资格。复用现存边界与用例，只补尚未贯通的证据。

首批已覆盖最新正文、原 Ref、预算和部分采用。文件从外部被改写后的冲突处置仍须由具体 App 验证。采用后传输中断是另一条故障路径，本轮没有注入。

第四批的串行采用测试覆盖了预览、部分采用、捕获期间停止，以及暂停后继续处理排队更新。第五批在实际 POST 后复现有效迟到及已放弃迟到，保留现有暂停和停止语义，按已证实的不完整工具流修复 LLMClient。已分发操作的持有及迟到终态仍由 Worker 和 Core 所有，定点回归覆盖等待超时、采用新观察、原收据及释放。[Worker 持有回归](../../runtime/src/engine/app/worker-host.scoped-interaction-e2e.test.ts)、[Driver 的串行采用回归](../../agent-driver-v2/tests/core/context-adoption.test.ts)

## 对后续研发的约束

1. 说明项目价值时，同时保留“外部事实界面”和“可受限操作的记忆界面”两层含义。
2. 任何优化都必须保持 Messages、Refs、Tools 来自同一观察；不得仅因文本缓存命中就跳过调用资格验证。
3. 不新增任意 Messages CRUD、通用长期记忆数据库或模型内部记忆 API；这些都不是本轮确认的范围。
4. 具体开页准入机制由 [10](10-opening-deferred.md) 暂缓，不在本定义中预设其实现。
