# Minimal Core Batch 12 · 用真实 App 明确 Ref 工具参数的作者写法

**范围是总计划 U0 的一个样例。** 交付物是一份可编译的作者用例、对应的当前运行记录，以及需要上级决定的最小接口差异。执行者只在隔离目录制作样例。共享生产、永久测试、公开导出、协议以及并行 SRT 工作树均只读。

## 要回答的问题

Planning App 已经向 Agent 展示当前计划和未完成计划的列表。如果一个只读工具要接收一个计划或整个计划列表，作者需要声明几次，模型传入什么，handler 实际拿到什么？今天能跑通哪些情况，哪一处限制迫使作者换成另一种 Tool？[实际发布方](demo-apps/planning-app/src/tui/PlanListView.tsx) · [已有真实 Ref 消费试件](runtime/tests/fixtures/dual-producer-app.mjs) · [总计划 U0–U2](MINIMAL_CORE_REFACTOR_PLAN.zh-CN.md)

## 执行范围

1. 锁定主工作树的实际 SDK/Runtime，以及一个明确版本的 SRT-01 作者候选。SRT 文件只用于对照已经存在的普通 Tool 声明和绑定，继续沿用该工作线自己的签收状态。无需重跑 M4 的四 App 迁移和通用作者试验。
2. 从 Planning 的真实发布代码和现有 Ref 消费试件取最小输入。在隔离目录用真实 SDK/Runtime 至少跑通一个现有对象 Ref，记录模型提交的名字、所属快照、handler 收到的值与业务进入次数。然后分开取样列表整体、单个元素。发布成功和作为工具参数消费成功分别记录。用实际返回或编译诊断说明受限情况。
3. 仅比较当前公开写法和一种最小的候选作者写法。候选沿用普通 Tool 的一次声明，把 Ref 当参数。用当前 TypeBox 与 TypeScript 的一个正例和一个反例检查 handler 类型，指出模型输入和业务参数之间要由哪个现有层完成解析。若当前包缺少表达能力，明确列出第一处缺口；临时类型试件不能充作已跑通的 Runtime。多 Ref 和可选 Ref 只标出这份写法能否表达，完整矩阵留给后续合同冻结。
4. 作者试件只走公开包入口，列明真实解析路径。不得用 `any`、业务侧手工查表、伪造 Ref payload 或另一套工具注册机制让示例过关。禁止迁移 App、删除旧 Hook、改变 Ref 名称作用域或 Observation 生命周期。

## 准出与交付

- 交回一张简短对照表，分别列出作者写的声明、模型参数、handler 值、行为证据，以及实验尚未覆盖的部分。
- 附实际输入身份、可复跑的样例与命令。若有需要决定的公开差异，给出具体写法、涉及的消费者和最小选择。能沿用现有合同的地方直接说明。
- 以 READY_FOR_REVIEW 交技术负责人。此批只为上级选择和后续迁移准备证据，不实施 R4 或 SRT-02，不提交、不发布。

## 给 Codex 的 Prompt

> 执行 Batch 12。以 Planning 的实际 Ref/ArrayRef 发布和现有 SDK 消费试件为例，在隔离目录回答“一个普通 Tool 怎样接收已有的计划引用”。先跑今天的公开入口，再用同一业务输入验证一种最小候选写法的类型。分别交回对象、列表整体和列表元素的结果，区分可编译、可运行和有待决定的行为。沿用 SRT-01 既有普通 Tool 接线，保留两条工作线的版本身份，交付可复核的样例、差异和最小裁决项。共享源码及公开合同只读。
