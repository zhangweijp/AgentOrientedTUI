# Batch 18 · 列表换了顺序，上一轮的工具会读到谁

同一个名字可以在先后两轮合理地代表不同对象。例子是“未完成计划列表的第一个计划”。负责人已在真实 Worker 把列表从 A、B 换成 B、A。保留旧上下文，又从默认 Source 预览新上下文，旧工具仍读 A，新工具读 B。显式释放旧上下文后，旧入口被拒绝，新入口仍读 B。这项对照使用手工持有的两个上下文。真实 Driver 在一次连续会话里何时释放上一轮、实际模型请求对应哪份数据，是本批要回答的事。[预览与显式释放的实测](review-evidence/minimal-core-batch-18/owner-review/preview-order.json) · [串行观察的目标与待定机制](deepseek_review.md)

**仅验证已有串行路径。** 生产文件白名单为空。用签收的 B16 组合包启动真实 Runtime、默认 Source 和 Node Worker，沿用 B13 已验证的真实 Driver、LLMClient、streamText 及受控 HTTP 响应方式。核对构建来源，说明哪些包来自哪份冻结输入。可从 B16 的原有 Planning 夹具衍生一个只更改列表顺序的副本。App 的实际业务 ID 必须不同，页面和模型传入的引用名字必须逐字相同。

**准出条件**

1. 让**同一个 Driver 实例**连续完成至少两次模型请求。第一次模型从已显示的列表读 A，随后通过现有工具提交重排；第二次模型面对已重排的页面，用相同的名字读 B。记录真实请求、工具参数、观察和绑定身份、完整业务实收、收据，以及触发续轮的来源。使用私有临时数据，不依赖外部模型或计费服务。
2. 在第二次模型请求实际抵达受控传输时，用第一轮捕获的执行入口再试同名调用。记录是否进入业务、实际读到什么，以及旧上下文释放与两次模型请求的相对顺序。明确区分“旧入口读同名数据”和“新一轮重新提交旧拼写”。用等待实际信号或受控屏障来划分时刻。
3. 用负责人已运行的手动预览作为对照，并验证本会话正常结束和模型请求在返回动作前失败时的清理。核对 release 次数、可观察的保留量、Worker 与待办任务结清、业务动作次数。区分调用资格、框架持有的观察/快照和 App 自己的业务数据。只报告能实测的层次。
4. 给出当前运行行为、已确认的“采用新观察后旧资格失效”目标，以及仍需决定的交接点。若发现旧入口能误读新对象、失败后重复执行、或旧数据无法证实已释放，保留首次证据、最小影响面和上级要决定的问题。提交可复跑命令、精简的原始记录及报告。

**复用开工对照的方法。** B16 复跑的 `candidate/consumer` 内，复制其源码、包链接和编译配置到新临时目录。只把样例 `app.tsx` 中的 `stage==='updated'?updated:` 换成 `stage==='updated'?[...updated].reverse():`。严格编译后，把 [负责人探针](review-evidence/minimal-core-batch-18/owner-review/preview-order.mjs) 放在该目录，用 `node preview-order.mjs <新的输出路径>` 运行。

本批不改 SDK、Runtime、Driver 或真实 App，不设计并发、已读回执、新状态管理器或自动重试。跨页命名、公开 API、共享包迁移和发布由各自的决策处理。旧 D3 迁移已经取消。

**给执行 Codex 的 Prompt**  
在一段真实 Driver 会话里，让两轮模型对同一名字先后读到 A、B。在第二轮到达时再用保留的第一轮入口尝试一次，检查它何时失效、是否进入业务。对照手动预览和模型失败后的释放，用真实收据和资源计数说明现行保证。按四项准出交 READY_FOR_REVIEW，生产补丁为空。
