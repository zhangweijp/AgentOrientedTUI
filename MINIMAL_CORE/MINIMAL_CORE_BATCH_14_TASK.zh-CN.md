# Batch 14 · 让同一份 Ref 参数声明能被程序实际读取

Batch 12 证明了 TypeScript 可以从一份计划定义推导出业务参数。它使用的 `RefValue` 只有类型签名。Batch 13 给出了一个真实反例，只有 `title` 的空计划曾经能进入工具。下一步用这两个结果检验总计划 U0 中的一件事。作者写一次“需要一份计划”或“需要一份计划列表”后，程序应能给模型一个名字参数，并检查这个名字对应的数据能否作为该参数使用。[已签收的作者样例](review-evidence/minimal-core-batch-12/revision-1/samples/candidate.type-prototype.tsx) · [U0 的约束](MINIMAL_CORE_REFACTOR_PLAN.zh-CN.md)

**范围是隔离的声明与校验样例。** 锁定 Batch 12 的 Planning 业务类型和 SRT-01 M4.2 包身份。可改的副本限于 SDK 现有 `src/tools/view-type-tool.ts`、`src/tools/typebox-schema.ts`、Runtime 现有 `src/core/tool/ordinary-parameter-contract.ts` 及本批专属的作者和验证样例。优先复用已有入口与已安装的能力，实际需要几处就动几处。共享源码、依赖清单和 SRT 工作树只读。命名在试件内临时确定，公开 API 和协议版本留给上级裁决。

**准出取决于四个可观察结果。**

1. 从一次 TypeBox 声明得到可执行的样例。作者分别声明一个 Plan、一份 Plan 列表，各自混入一个普通参数。模型收到的 Ref 字段是名字字符串，普通字符串保留原义。严格类型用例实际把业务值传给接收只读 Planning 类型的函数。
2. 将声明导出为 JSON 并在独立进程读回。另一个进程仅凭声明即可区分单对象和整份列表，并识别支持的数据约束。改变业务类型或对象/列表形状时完整合同身份必须不同，即使模型看到的都是字符串。给出实际产物和首次失败位置。
3. 用真实 Planning 发布方捕获的单个计划、列表、列表元素及首版的占位对象作输入。合法值通过，只有标题的对象、对象与列表错配、非法嵌套状态被明确拒绝。保留既有输入上限，超限给出可复跑的拒绝。区分“已取得快照值后的结构校验”和“有资格读取该值并进入业务”，后者仍属于已有 Core/Worker 边界。
4. 用原有包对照一次，记录它面对候选声明的实际结果。未实现这种合同的执行入口必须拒绝，不能把带引用的参数降级成普通字符串后进入业务。交回来自隔离基线的样例增量、正反例、可重复命令，以及作者新增的手写声明数。若既有编译器在某一层无法表达所需结构，保留最小失败原件并说明所需的最小决策。该情形作为待决缺口交回，不记作已贯通。

本批实施止于参数合同，不接通线上执行路径。跨 View 寻址、授权放宽、观察切换、Worker 握手版本、公开导出变更和 App 迁移不在本批范围。不要另建注册中心、复制一套参数引擎，或要求 App 作者手查引用。

**给执行 Codex 的 Prompt**  
在隔离副本把 Batch 12 只有类型的 Ref 参数样例变成可运行的声明与校验。用同一份 Planning 声明分别说明模型传什么、程序知道应当得到什么、合法与错误的快照值会怎样处理。在新进程读回 JSON，证明两种参数形状能区分，普通参数保持原行为。复用现有 SDK/Runtime 的参数入口，附最小增量、真实输入和可复跑结果，交 READY_FOR_REVIEW。共享树和 SRT 保持只读。
