# Batch 19 · 谁还需要上一轮的数据

Batch 18 已经在真实会话里看到，第二轮开始前，第一轮工具失效，但按快照 ID 仍能从 Runtime 查出旧计划的完整内容。负责人还用两份真实 Worker 数据验证了默认十分钟的历史期限。在没有读者时，到期后的首次查询清掉旧快照。在另一位合法读者仍持有它时，旧数据仍可读，直到最后一位放手。[同一组数据的期限对照](review-evidence/minimal-core-batch-18/owner-review/history-window.json)

项目目标要求旧观察专属数据及时释放。现有 R5 同时保留了按快照 ID 查询历史的公开能力。要交项目所有者决定的是，哪些既有使用方式需要完整旧内容，哪些只需要收据、身份或当前数据。**本批只核对影响，不更改默认保留时间、容量、公开接口或生产实现。** [产品约束](AGENTS.md) · [现行 R5 合同](MINIMAL_CORE_REFACTOR_PLAN.zh-CN.md)

## 准出条件

1. 从实际导出的 Core、Host/Worker 和 Source 入口反查旧快照的使用者。把按历史 ID 新发起的查询、另一份仍有效的观察、已完成工具的收据回读分别列出来。指出谁授予读取资格、何时释放、谁还需要完整 Ref 内容。按已支持的公开合同、仓内真实调用、仅测试用法分类。仓外采用率未知。
2. 沿用已签收的构建组合与 B18 的真实 A/B 数据。用现有公开接口顺序建立两份有读取资格的观察，释放其中一份，再从另一份合法观察读 A。证明当前仍读 B，已释放的观察不能发起新业务。随后释放最后一位读者。用已有的可控时钟或只在隔离试件中改变历史期限，核对完整旧数据还能否经历史 ID、准确的 Ref 来源重新取回。把“活读者需要数据”和“无人持有也能重新查询”分列。
3. 在仍有权读结果的 Scope 中执行一次真实工具调用并取得收据。释放该观察，让历史源确实查不到，再用同一个 `ScopeClient.invoke` 重交完全相同的请求和调用 ID，检查回读的收据。另用新调用 ID 尝试从已释放的观察发起新业务。核对每次读取的权限、结果内容、业务进入次数，再做一次不允许读取的对照。区分 Scope 关闭与其中一个观察释放。优先复用已有核心回归，只补能区分这几种责任的探针。
4. 给出一张可以据以裁决的影响表。如果“最后一个合法读者释放后，立即删除旧 Ref 内容”，明确哪项调用结果会改变、哪些可独立保留，以及哪个边界属于公开行为变更。给出最小影响面、未覆盖的消费者和独立复跑命令。已签收的 B18 会话及十分钟实测只作输入引用。

生产补丁为空。复用现有 SnapshotStore、Scope、收据和释放合同。不得新增历史仓库、兼容层或回退，不额外保留另一套 payload，不以按名字查询最新快照绕过权限。无需改真实 App、SDK、Worker 协议、历史消息或 Git 状态。报告区分现实与方案，交 READY_FOR_REVIEW，由技术负责人复核。

**给执行 Codex 的 Prompt**  
查清上一轮的完整数据今天究竟为谁保留。用同一份真实 A/B 输入，依次验证仍持有观察的第二位读者、只有历史 ID 的调用方、只想回读已完成收据的调用方。给出各自的真实结果、权限和业务次数，说明立即清除旧 Ref 会打破哪条已支持合同。只做隔离取证，交四项准出和空生产补丁。
