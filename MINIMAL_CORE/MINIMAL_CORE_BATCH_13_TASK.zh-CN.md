# Batch 13 · Planning 没有当前对象时，Agent 能拿到什么？

**授权范围：隔离复现和修复候选。** 首页没有选中的计划时会显示 “No active plan.”，详情没有进行中的阶段时也有相应说明。两个页面今天仍然发布一个只有标题的对象。Batch 12 的真实 Worker 证明：在授予该页所有引用的宿主策略下，通过现有工具传入 `active_plan` 会把这个占位对象交给业务。生产宿主使用的 [Semantic Source](runtime/src/adapters/semantic-aotui-driven-source.ts) 还会把该页授予的名字附在发给模型的 View 末尾。要从实际模型请求验证影响，再交一个作者能照着写的最小修复。

负责人已另用**默认 Source**复现首页现象：同一条消息正文写着 “No active plan.”，末尾却有 `active_plan (unknown)`，传给工具后得到成功和 `planId: 'unknown'`；整份列表的名字也在末尾，但传给工具被拒绝。[修复前的完整消息与工具结果](review-evidence/minimal-core-batch-13/owner-review/default-source-trace.json)。这个探针没有经过 Driver。请将它作为独立对照，执行侧仍需覆盖下述 Driver 与阶段场景。

**想验证的候选行为：** 有当前计划或阶段，页面沿用原名发布真实业务对象；没有就只显示原提示，该轮的新观察不把它列为可用引用。真正存在的空列表仍是有效列表。是否将候选应用到共享树或并行 SRT，由负责人核对实际差异后另行处理。这里不决定统一 Ref API、改变旧观察有效期，或改写业务操作。

1. 在私有目录基于实际字节重建。生产候选白名单只有 `demo-apps/planning-app/src/tui/PlanListView.tsx` 与 `demo-apps/planning-app/src/tui/PlanDetailView.tsx` 的**副本**。额外样例、驱动与测试只放本批证据或私有目录。沿用现有 SDK 的挂载/清理能力；不要改 Hook 签名、新建框架辅助层、手查 Ref 表，也不要只过滤消息正文。
2. 用真实页面、SDK、Runtime 和 Node Worker、默认的 `SemanticAOTUIDrivenSource` 取上下文；至少一条路径经过真实 Driver，把受控模型收到的消息和工具参数留样。外部模型不在范围。分清页面正文、末尾可用引用、实际授权/拒绝、业务进入。确认旧版的两种占位现象能否复现，不能从首页类推到详情。复现不了的路径报告事实，不扩改。
3. 分别验证没有、出现、退出当前计划/阶段后**新取得的上下文**。有真实对象时保留名字、可读正文、完整业务值与既有工具；没有时保留提示、对应名字不在可用引用中，强行用该名字调用也不能进入业务。至少一个列表及其元素作为对照；列表有名字不代表整份列表已能作为工具参数。记录收据，以及关闭后的资源结果。不要从旧观察得出新规则。
4. 交付与开工副本可正反应用的两文件增量（如少于两份则按实报）、先失败后通过的真实对照、精确构建输入及一条复跑命令。同时说明：删除了哪两处假数据，哪些资源仍由 Runtime 管，App 作者是否增加了概念。发现独立问题记下，不扩到 Driver、SDK、Runtime 生产修改。
