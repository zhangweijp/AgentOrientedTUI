# Batch 17 · 两个页面里的同一个名字，工具会读到谁

Batch 16 已验证，Planning 标为计划的列表元素可由现有只读工具读取。负责人还使用了与 Agent 相同的默认入口。在同一份上下文里，模型能看见主页面和另一页各自的计划名。主页面的工具能读本页的计划，读另一页的名字得到 `REF_NOT_VISIBLE`，业务进入零次。[默认入口实测](review-evidence/minimal-core-batch-16/owner-review/default-candidate.json)

现有只读工具绑在某个页面实例上。目标中的普通工具按页面类型共享，可以有多个引用参数。若将来只给工具一个名字，两个页面都发布这个名字时，就必须知道应拒绝哪种情况。总计划 U3 提议让名字在同一 App 内唯一；旧应用实际使用什么、改变作用范围会影响谁，需要实证。[总计划 U3](MINIMAL_CORE_REFACTOR_PLAN.zh-CN.md) · [现有名字合同与待决点](deepseek_review.md)

**本批只做取证和迁移影响评估。** 允许在本批证据目录和私有临时目录编写最小 App/Host 探针。冻结原包和签收的 B14、B15、B16 参数与发布候选是运行输入。共享树、SRT 工作树、既有 App、SDK、Runtime、Driver 与历史交付均只读。证据记录实际包来源和指纹。用已封存输入复跑，直接引用历史原件，避免复制整套历史日志。

**准出条件**

1. 在同一 App 两个同时挂载的页面发布**逐字相同的名字、相同业务种类、不同业务 ID**。先用两个不同名字作对照。在真实默认 Source 的同一轮消息里逐页列出名称和已呈现的工具，再从其实际执行入口调用。若可分别读取，要记录哪个页面的工具读到了哪个完整对象；若框架拒绝，要给出首个错误、发生位置和业务进入次数。额外取一个实际存在但没有授予的对象作对照。把默认可见范围与自定义 Host 授权分开。
2. 按串行顺序更新其中一份数据，再卸载该页并重新取得上下文。核对另一页、同名后继发布者、已经显式释放的上下文各能读到什么，业务实际进入几次。区分同页已有的重名保护与跨页现象。通过现有入口测量，只要代码中存在的行为；本批不定义“何时视作 Agent 已采用新观察”。
3. 核对仓内真正发布 Ref 的 App 调用点、动态名字和可同时打开的页面。至少实际运行一个原有 App 的原有页面组合，记录观察到的重名或无重名，以及样本边界。试件能制造重名与现有 App 确有重名要分别报告。共用工具的 App 作者需要加什么额外参数、处理什么失败，一并列清。
4. 给上级一张可决策的对照，讨论“同一 App 内名字唯一，发布冲突时明确拒绝”与“名字由页面区分，调用时必须有确定的页面身份”。逐项说清哪里检查、冲突影响哪个页面或 App、会影响哪些现存写法、能否避免误读另一个对象。若有未能实测的后果，标为方案推论。形成可重跑命令、签收基线、实际收据和精简报告，交 READY_FOR_REVIEW。

本批交付的生产补丁应为空。不得改名字或自动加前缀、查询最新 AppKernel Map、放宽授权、实现跨页解析、改 Worker 协商、创建另一个 Ref 注册中心，或让 App 自己检查框架的归属。共享迁移、公共 API 与发布由上级另定。

**给执行 Codex 的 Prompt**  
从签收的 Batch 16 组合包出发，让两页用同一个引用名指向两份不同的计划，沿真实 Agent 入口查明各次调用读到了谁。用真实 App 验证这种命名在现有项目里是否存在。交出四项准出和一份让项目所有者能直接决定命名范围的短说明。只写隔离夹具和本批证据，不改生产代码。
