# Batch 21 · 给普通工具读取一份计划建立可执行的验收

作者想写一条工具声明，表达“给我页面上那份计划”。Agent 传一个名字，业务函数收到当时看到的完整计划，返回操作收据。工具仍由同类型页面共享。这个方向已经确认。目前给普通工具写这条声明，SDK 能接受，Runtime 注册时会拒绝。在同一套包里，专门绑定页面实例的旧工具可以读取它。[签收的实际包](review-evidence/minimal-core-batch-20/final-delivery.json) · [已确认的目标与 U0/U5 边界](MINIMAL_CORE_REFACTOR_PLAN.zh-CN.md)

**本批交付一份能交给下一位开发者直接跑的作者验收，以及达到它所必需的协议改动提案。** 验收只选 Planning 当前唯一可见的一份 Plan、一个必填输入、串行读取。跨页重名、多个引用、列表和保留期限各有自己的裁决。当前签收包应当在普通工具的目标用例上报出真实失败。以后实现接通时，使用同一个业务成功断言。

## 三项准出

1. **从作者写 App 的正常入口复现。** 用 B20 已签收的私有 SDK 与 Runtime tar 严格编译一个小 App。复用原有 Plan 数据、B14 的本地声明样例和公开的普通工具绑定，把业务函数、参数、期望收据写清楚。让真实 Worker 装载，默认 Source 尝试取得普通工具并用页面上的名字执行。现有版本在注册、App 初始化或投影中途拒绝时，保留第一条可定位的错误、Host 实际能看见的结果和业务进入次数。用正常工作的 App 或同一页面的既有单引用入口作一次正向对照。单独保存“目标业务必须成功”的测试及它在当前包上的预期非零退出，不通过改写业务预期来制造绿灯。
2. **证明保护究竟在哪一层。** 普通工具的执行身份属于一类页面。引用的来源属于它当时获准读取的快照和具体页面。用现有 Host/Worker 的协议入口对照合法普通调用、合法的实例引用调用，并检查试图把两者的字段或身份混用、缺少所需能力时，真实接收端如何处理。优先用已签收的试件和定向测试，仅补能观察到原始请求、响应和业务次数的一处。正常输入、所见的计划和业务实收应可追溯；遇到异常行为保留最小反例并升级。负责人已有严格编译的正反例和四种实际装包结果，可直接引用。[现有消息类型对照](review-evidence/minimal-core-batch-20/owner-review/wire-ownership.json) · [实际包组合](review-evidence/minimal-core-batch-20/owner-review/package-pairs.json)
3. **交一项可裁决的改动。** 依据上述实际调用，给出让这一条普通声明成立所需的最小协议差异。至少说明原始名字、已解析的值及其来源由谁提供和核验，如何保留普通工具的激活身份，怎样让授权看到的值与业务收到的值一致。若涉及新的能力标识，可在独立的类型样例中给一个明确的提议，同时列出新旧 SDK、Host、Worker 相遇时应当发生什么；逐项标出实测和待实现。指出可直接复用的现有方法，以及需要修改的精确文件与归属。让上级能够一次决定这个小范围是否可以进入隔离实现，再由同一作者验收先红后绿。

## 白名单和交付

共享写入仅限本批报告、空生产补丁、`review-evidence/minimal-core-batch-21/` 的新试件与证据。App 源码和协议类型试件写在该证据目录或自己的临时目录，使用现有包和本地依赖。B20 的 tar、声明、原报告与证据通过签收指纹引用；保留本批新发生的命令、首个失败和必要原始输入输出即可。

共享生产文件、其他工作树和已封存档案只读。保留现行握手、权限和旧工具入口；不得用普通工具偷偷调用旧 Hook、按名字去全局查最新数据、接受调用方自带的计划对象或改成按实例注册。协议提案只作提案。本批不派生新的正式能力、公共 helper、兼容层或模型作者试验。交 READY_FOR_REVIEW，由技术负责人独立签收。

**给执行 Codex 的 Prompt**

拿 B20 的实际包写一个最小 Planning App，让普通工具只声明一次“需要一份计划”，把成功条件写成可复用的端到端测试。从真实 Worker 启动到 Source 调用，留下现在第一处失败和已有单引用路径的成功对照。再拿当前接收端核对普通工具身份与页面引用来源能否混用。交一个精确到字段、现有模块、旧端行为的升级提案，供负责人裁决；共享生产代码不动。
