## 一次调用要让作者得到什么

沿用 Batch 21 的同一个 App。作者只在 `read_plan` 的普通工具声明中写一次“需要一份 Plan”。Agent 传页面显示的名字。框架查出这次观察确实获准读取的原计划，授权策略、Worker 和作者的函数收到内容相同的值。作者返回计划编号作为收据。两处身份都要能追查。工具属于 App 中一类已打开的页面，数据属于当时那一个获准页面的快照。业务代码只处理计划。

## 准出条件

1. **同一个作者 App 先失败再成功。** 基线实际注册拒绝。新包的真实 Node Worker 从默认 Source 运行同一份未改写的作者程序，传 `Plan:plans[0]`，业务一次收到原始完整 A，得到 `plan_a` 收据，随后释放。关联实际观察、原绑定、执行授权、分派、请求和响应。普通工具持有正确的 ViewType 激活，Ref 来源能在原观察的授权和原快照里逐字段对上。授权、分派和业务值内容一致。模型输入仍是名字。普通数字工具 2 加 1 得 3。同类型两页共用该工具时保住既有共享规则，可复用现有真实测试。两个会让旧验收误过的故障副本仍分别因执行身份、引用来源而被修订验收拒绝。
2. **拒绝路径能分清谁负责。** 用一页真实更新的补充对照检验数据来源。每次只授予一个同名引用，让仍持有合法旧观察的调用读 A，新观察读 B，旧 Context 显式释放后拒绝。这样能抓住写死 A 或偷偷查询最新页面的实现。Agent 直接上传对象、猜测未授权的名字、选择错误业务类型或失效的工具时，均有明确拒绝，业务进入 0 次。观察仍有效但执行政策拒绝时，Worker 收不到业务请求。在异步授权未结束时用受控屏障撤销原资格，恢复后仍不能派发。Worker 独立拒绝合同、来源字段或执行身份互不相符的请求。验证跨进程传的是同一份内容。Worker 能检查消息形状与当前注册，只有 Host 能证明原观察确实授权。使用已有预算与真实关闭检查。
3. **新旧端逐项给出实际结果。** 让新旧 SDK 工厂和 Runtime 相遇，并把同一真实 Host 和同一真实 Worker 分别与旧、新对端组合。原包合法数字及旧页面引用用例先跑通。目标组合须能按普通工具读 Plan 及数字。版本错配按提案在对应能力或工厂握手处明确拒绝，拒绝发生在业务执行之前。分开记录接收端与公开 Host 的错误、Worker 请求数和业务次数。使用真实构建产物与接收端，单改版本常量的对照需单列。保护现有健康 App 和超时/关闭结算。不要尝试回退为实例工具、普通字符串或从当前页面重新查值。
4. **交可以独立复跑的样机。** 列出哪些解释或分支被消除、原有哪个模块继续拥有提交/观察/授权/执行，附每个实际修改文件的理由。交签收基线至样机的补丁、装包来源、作者红绿、负面用例及相关 SDK/Core/Worker 既有回归。一次干净复跑能重建候选。作者新增手工解析、二次声明和自行授权步骤都应为零。交 `READY_FOR_REVIEW`，由技术负责人独立复验后裁决。

本批只选一个 App、一个必填的单项引用、一次串行调用。重名策略、列表/多选、历史数据寿命、旧入口退出与四个 App 的迁移各有单独范围。保留 R4 已经证明有独立职责的检查。负责人需单独批准采用隔离成果。
